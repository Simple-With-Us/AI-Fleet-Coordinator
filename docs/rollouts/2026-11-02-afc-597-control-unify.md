# AFC-597 S3: one control path, a wider allowlist, and a log tail

Date: 2026-11-02. Lane: muse-code/afc-597-control-unify.  This slice unifies service control on the OpsController plan, Touch ID, re-plan and run path, widens the fleet-ops-control allowlist with pm2 applications, and adds a bounded read-only log tail for allowlisted server units.  Nothing in this slice was run against a live service.  Every new verb is covered by fake-runner tests, and the visual check pressed no action button.

## What changed

The helper gained a pm2 scope.  A pm2 verb is one argv, a pinned node plus the pm2 script plus start, stop or restart plus the application name, with no shell and no ecosystem fallback.  The allowlist names ten pm2 applications under mac.pm2Apps.  Those names were copied exactly from the Muster fleet service registry, and a test asserts that every allowlisted pm2 name still appears in that registry's source.  A name must match a strict lowercase pattern before it reaches an argv, and an unlisted name or a disallowed verb is refused.

The helper gained a server logs verb.  It is planned and run like every other verb, so Touch ID gates it in Muster uniformly, and a plan carries no log text.  A run returns the last 200 journal lines for one allowlisted unit through one journalctl argv with no pager and no follow, truncated to 64 KiB with a truncation note in the output when anything was cut.  That returned text is the one deliberate exception to the old rule that helper output is thrown away.  The audit still records no log text.  A finished logs run records the target and the line count only.  Mac LaunchAgents have no log verb, because launchd has no uniform log file to tail, and inventing per-agent log paths would have widened the helper past what this slice specified.

No server unit was added.  The server-status collector reads its unit list from this same allowlist, so the only units named repo-side are the two timers already allowlisted, fleet-server-status.timer as a user unit and fleet-cli-git-update.timer as a system unit.  Widening therefore means logs for those existing units plus the pm2 applications above, and nothing else.  No unit name was invented, and no new verb was invented for the timers.

Muster gained two actions.  A pm2 action runs the helper on this Mac, and a logs action goes over ssh to the same forced-command alias as the other server verbs.  The answer parser surfaces log text only for a logs run that ran, never for a plan and never for any other action.  The plan sheet shows that text in a scrollable, selectable block after the run, so the owner can copy it.  The Server Status panel shows a Logs button beside Start, Stop and Restart for a controllable unit.  It inherits the panel's stale discipline, because the services section only renders for a current report, so a stale report offers no Logs button just as it offers no other server action.

The Fleet Services panel now actuates through the one path.  A pm2 row plans a pm2 action and a LaunchAgent row plans a Mac agent action, and the sheet's plan and Touch ID step replaces the old stop confirmation for those rows.  UI text was otherwise left unchanged, because the panel has no cheap per-row label affordance for naming the path, and the sheet itself already says where an action runs.

## What stayed where it was, and why

The BotFleet Server's own card and its row stay on the fleet admin.  Its start clears the deliberate-stop marker through the installed wrapper, and its stop asks the server itself through its control API, because launchd does not always own the process.  Neither behaviour is an allowlist argv, so neither moved.  The two login-item toggles stayed for the same reason.  The menubar fleet admin menu also stayed, because this slice named the panel, and the menu still actuates through the fleet admin with its stop confirmation.  FleetAdmin and FleetServiceControl therefore remain fully referenced, by the server's special path, by both login toggles, by the menubar menu and by every read the panel shows, so no start or stop code became dead and none was removed.

One row needs an owner decision.  The BotFleet Companion row now plans through the helper like every other LaunchAgent row, but its label, app.botfleet.companion, is not in the allowlist, so the helper refuses it in the sheet until the owner adds that label to fleet-ops-control.json.  This slice did not add it, because widening the Mac agent list was not specified, and the helper must fail closed.  The companion remains controllable from the menubar menu in the meantime.  The pm2 start verb also has no ecosystem fallback, unlike the fleet admin's pm2 client, so starting an application pm2 no longer remembers will fail in the sheet rather than recreate it from the ecosystem file.  That is deliberate for this slice and worth a follow-up if it bites.

## Install and verification

The server side needs no new install step beyond the existing helper rollout.  The ssh forced command already runs the helper, and the logs verb is accepted by the same gate with the same one-target, plan-or-yes shape.  The Mac side needs the helper and the allowlist from this checkout, as before.  No live run was made from the CLI or the UI, no logs were fetched from the server, and no Touch ID prompt was answered.

Tests came first.  The Python suite covers a logs plan refusing a non-allowlisted unit with no log text in the answer, the exact bounded journalctl argv for both scopes, truncation past 200 lines, an audit line holding the count and none of the text, pm2 argv for an allowlisted application, and pm2 refusal for a bad token, an unlisted name and a disallowed verb.  The Swift suite covers the pm2 and logs argv, token refusal, allowlist parsing for pm2 applications, and log text surfacing only for a finished logs run.  Observed results: 46 Python ops-control tests passed, 64 server-status tests passed, 18 Mac services tests passed, and the full Muster suite ran 638 tests with 1 skipped and 0 failures.  The visual check launched a Debug build, captured the window alone, and confirmed the Fleet Services rows and the Server Status panel render with Logs buttons on both controllable units.  Screenshots are at /tmp/afc597-shots/muster-services.png and /tmp/afc597-shots/muster-server-status.png.  The launched instance was quit by its own pid, and no other Muster instance was touched.

## Unresolved

The companion allowlist decision above is open.  The menubar menu still actuates through the fleet admin, so unifying it is a follow-up rather than part of this slice.  Live proof is still missing by design: the first real pm2 and logs runs should be one owner-approved plan each, read in the sheet before Touch ID, after this lands.
