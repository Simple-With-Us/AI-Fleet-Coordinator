# Eavesdropper Status On The Server

Muster shows what the listener (the eavesdropper) is doing: which seats are connected and running, which are paused, which are held by a quota, and what each seat holds back.  The eavesdropper writes that as `status.json`, a document for its own operators that carries filesystem paths, Zulip user ids, topic keys, session ids and config error text.  None of that belongs in an app, so `scripts/reduced_status.py` cuts the document down to names, counts, tokens and times (the `reduced_status` v1 schema, described in that module's docstring, including every field the source does not carry and so leaves null).  Lease titles are never emitted, by the design owner's privacy ruling: the lease objects have no `title` field at all.  The Mac reduces its own listener's file directly.  The server's side goes through the restricted helper, so the app never needs a new SSH key, a new alias or a broader grant.

The helper gains one read-only verb, `server eavesdropper-status server --plan --json`.  The target is the instance word `server` and nothing else, because the container it reads is the server's.  It takes no action lock, asks for no sudo and writes no audit row for a plan; `--yes` is refused (and audited, as every refused `--yes` is), and any other target is refused.  The verb needs no allowlist entry and reads none, but the helper loads and validates the allowlist file before it dispatches any verb, so a missing or invalid allowlist refuses this verb as it refuses every other.

## What The Read Uses

The read is one fixed argv, run without a shell: `docker exec --user simpletools eavesdropper /bin/cat /data/listener/status.json`.  The container name, the user and the path are constants in the helper (`/bin/cat` is named in full, so no PATH inside the container is consulted), and no word from a request reaches docker.  The privilege is the account's membership of the `docker` group (the socket is `root:docker`, mode 0660), which the helper's account already has; no sudo, sudoers entry or root shell is used.  `--user simpletools` runs `cat` as the container's own unprivileged account, which owns the file (mode 0600), so the read is no wider than that account's own.  `/data` is the daemon's `SIMPLE_TOOLS_STATE_DIR`, a docker volume, and the listener's `listener_dir` puts `status.json` at `listener/status.json` under it.

The docker call's environment is built by the helper and nothing of the caller's is passed: `PATH=/usr/bin:/bin`, `DOCKER_HOST=unix:///var/run/docker.sock`, and an empty private temporary directory as both `DOCKER_CONFIG` and `HOME`, removed afterwards, so no docker config, context, credential helper or proxy setting of the account can apply.  The reader is the helper's own bounded one (`run_bounded_read`): it stops at the first byte past 1 MiB, kills docker at once and answers `too_large` without waiting for the 15 second timeout, keeps only the first 4 KiB of docker's stderr, and waits for a killed child only for a few seconds.

When the status cannot be read the answer is not a refusal and not a failed command: `ok` is false, `result` is `unavailable`, `errorCode` is one of `docker_unavailable`, `timeout`, `container_not_running`, `read_failed`, `too_large`, `not_json` or `module_unavailable`, and the exit status is 1 (the one case in which the exit status is 1 although no command failed).  `container_not_running` is chosen by comparing the start of docker's stderr with its known phrases for a missing, stopped or restarting container (`No such container` was seen live; `is not running` and `is restarting` are the engine's wording from its source and were not seen live, because the live container is not stopped to try it); any other failure is `read_failed`.  The answer never carries a path, docker's text or any byte of the file.

## The Reducer Module

The helper does not import the reducer.  It opens the helper's own folder and then the module file with `O_NOFOLLOW`, so a symlink anywhere in that chain is refused, judges the folder and the file by `fstat` on the descriptors it opened, reads the bytes from the file descriptor, and compiles and runs them in memory into a fresh module object: no `sys.path`, no `__pycache__`, and no second look at the path, so a file swapped in after the open changes nothing.  The module has one place, `reduced_status.py` beside the helper: flat in the installed folder on the server, and in `scripts/` of a source checkout (it is not in the `simple_tools` package, which the fleet CLI release ships under a file budget).  The layout is read from who owns that folder.  A folder owned by root is the installed layout: the folder and the file must be root's and writable by neither group nor others, and the calling account's own ownership is never enough there.  Any other folder is a checkout: the file and the folder may be the calling account's, still with no group or other write bit, and a checkout owned by another account is refused.  On a server lane, whose files are group-writable, run `chmod g-w` on `scripts/` and on `scripts/reduced_status.py` first (and restore them after), or use the installed copy.  A module that is missing, untrusted, too large, unloadable or without `reduce_status` answers `unavailable` with `module_unavailable` before docker is run.

## Deployment

The server CLI checkout update does not replace the protected broker installation.  This change needs three files under `/usr/local/lib/fleet-resource-control`, installed the way the seat inventory verb was (see `2026-11-06-seat-inventory-verb.md`, whose Deployed section records that procedure with its hashes) and the AFC-607 helper repair before it: a hash-verified backup of the current `fleet-ops-control.py` and of the current `fleet-ops-control.json`, each new file installed beside its installed one as a candidate, its hash verified against the repo file, and an atomic rename for each.  The order is the module first, then the allowlist JSON, then the helper.

- The module goes in as the flat file `reduced_status.py` (copied from `scripts/reduced_status.py`), owned by root with mode 0644 in the root-owned folder, because the helper refuses a module whose owner is not root or that group or others can write.
- The allowlist JSON is replaced in the same deploy because the installed copy is older than `main`'s.  The server's copy carries the Mac section too, and it must name the Mac's runtime-sync label `com.jay.simple-tools-runtime-sync` with its actions (start, stop, restart).  Its backup is kept with the helper's, and rollback restores both.
- The helper goes in last.  It loads the allowlist before every verb and the module when this verb runs, so a helper that finds no trusted module answers `unavailable` with `module_unavailable` instead of failing, and a wrong order costs an unavailable answer and nothing else.

Rollback restores the two backups (the helper and the JSON) through the same candidate-and-rename procedure and removes the module.  Do not run the full installer or change sudoers, SSH, units or settings.  (`scripts/hetzner/install-resource-control.sh` now names `reduced_status.py` in its fixed payload, reading it from the scripts folder beside the helper's own files and installing it flat, so a later full installer run installs it too.)

Ship the Muster build with the Mac and Server switch first or last, in either order: a build that asks for the verb before the helper has it gets the helper's refusal ("unknown server verb"), which the panel shows in words, and a helper that has the verb before the build asks for it does nothing.

- `python3 scripts/test_fleet_ops_control.py` (the verb's tests are `EavesdropperStatusDispatchTests`, `ReducerModuleTests` and `BoundedReadTests`) and `cd scripts && python3 -m unittest simple_tools.tests.test_reduced_status` (the reducer, the hostile inputs, the lease titles that must never come out, and a real `Daemon.status()` document).
- `python3 -m unittest discover -s scripts/hetzner -p test_install_resource_control.py` (the payload now names the module).  On Python 3.14, `test_symlink_destination_directory_refused` fails the same way on `origin/main` without this change.
- After deployment, through the Mac's real route: `ssh fleet-ops-ctl -- server eavesdropper-status server --plan --json` returns `result: planned` and a `status` with `schema` 1 and `instance` `server`, and `--yes` returns `refused`, and any other target returns `refused`.
- The same answer must list the server eavesdropper's own seats (its `seats` array is not empty) and a `status_updated` within the last minute (the daemon rewrites the file every two seconds), and those seats must read `running`.  That is what proves the helper read the live container's file and not an old copy.  A `status_updated` older than five minutes, or more than five seconds ahead of the helper's clock, makes every seat `unknown` by design.
- The allowlist after the deploy: the installed `fleet-ops-control.json` has the sha256 of the repo file, names `com.jay.simple-tools-runtime-sync` exactly once, and the helper still loads it, which any `server ... --plan` answer proves because the allowlist is loaded before every verb.
- The label, on the Mac, from a copy of the helper that holds this change: `python3 scripts/fleet-ops-control.py mac restart com.jay.simple-tools-runtime-sync --plan --json` returns `planned` with one `launchctl kickstart -k gui/<uid>/com.jay.simple-tools-runtime-sync`.  It is a plan and changes nothing.  `AllowlistTests` in `scripts/test_fleet_ops_control.py` runs that call against the repo allowlist with a fake launchctl, and Muster's `ServiceReconcilePolicy` table names the same label (its test compares the table with the file).
- `python3 scripts/test_fleet_cli_release.py`: the fleet CLI release ships `simple_tools/` under a 155-file receiver budget, which is why the reducer lives in `scripts/` beside the helper and not in that package.
- An answer of `unavailable` with `module_unavailable` right after the deployment means the installed module is missing, not owned by root, or writable by group or others: check `ls -l /usr/local/lib/fleet-resource-control` for `reduced_status.py` and the folder.
- No string in the answer may look like a path, an email or an id.  There is no free text in the answer: lease titles are never emitted, so a title can never carry a path, an email or a key out, and the answer's lease objects have no `title` field.
- Do not stop the live container to try the unavailable path: the unit tests cover every reason word, and a stopped container answers `container_not_running`.
