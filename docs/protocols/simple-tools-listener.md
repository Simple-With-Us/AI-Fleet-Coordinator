# Simple-Tools Listener

The listener is the capture half of the one wake path.  It holds the Zulip queues, decides at zero tokens which messages wake a seat, writes each one to the seat's inbox and hands it to the seat's router.  The router's half is [zulip-wake-routing.md](zulip-wake-routing.md).  Code:  `scripts/simple_tools`.

## Summary

One always-on daemon, `simple-chat daemon run`, runs on the server and holds one Zulip event queue for each seat in its config.  It spends no model tokens.  For each message it decides whether the message reaches a live session that follows the topic, the seat inbox, or both, and whether it wakes the seat.  A seat either has a `routine`, an HTTP POST to the seat's router, which picks a chat, delivers and wakes it, or it captures only.  Zulip text that reaches a model is always wrapped as untrusted data.

## Goals and Constraints

- Zero model tokens in the listener.  It starts no model run of its own.
- Capture first:  every message that should wake a seat lands in the seat inbox, whatever happens after.
- Zulip content is untrusted data, including a message from the owner.  The woken chat screens a peer's request under FLEET-PROTOCOL Precedence rule 3.
- Agents never create accounts and never touch the owner's personal key.  Credentials are read only by the `simple-chat` code, from Infisical Fleet-OPS `/zulip` (`<BOT>_ZULIP_EMAIL`, `_KEY` and `_SITE`, through `fleet-secrets`), or from the environment on the server instance.

## 1. Architecture

```
Zulip realm ──long-poll (one queue per configured seat bot)──► simple-chat daemon (the server)
                                                                  │ router.py (zero tokens)
            ┌──────────────────────────┬──────────────────────────┼───────────────────────────┐
  live lease inbox files       seat inbox file            routine POST                  notify-owner
  (hooks / rewake / wait)      (inbox --local)            simple-tools-wake/1           (owner queue)
                                                          └─► the seat's router picks, delivers and wakes
```

The daemon is one process:  one poller thread per seat bot, the router on the main thread (it also runs the periodic `tick`), and one wake worker per seat that has a `routine`.

The listener runs as one instance on the server ([eavesdropper-server.md](eavesdropper-server.md)).  `docs/protocols/simple-tools-partition.toml` gives every seat to an instance (`mac`, `server` or `none`), and **a seat must never be configured in two listeners**, or each would hold a queue for the same bot and each would wake it.  The partition fails closed.  A daemon refuses to start, before the flock and before any register, when its `listener.toml` holds a seat that the partition does not give to its own instance:  a seat of the other instance (by the partition file, or by the seat's own `instance` key), a `none` seat, or a seat the file does not list.  It also refuses when the partition file is missing, when a section reads another listed seat's credential under its own name, or when its `SIMPLE_TOOLS_INSTANCE` differs from its config's `[daemon] instance`.  At connect, a key whose `users/me` is not the seat's own bot is refused.  A reload that would add a seat this instance may not hold is refused, and the running config stays.  Details:  [eavesdropper-server.md](eavesdropper-server.md#seat-partition).

- **Code:**  pure stdlib Python 3.11 or later.  `zulip.py` (client, 429 handling, redirect refusal, key scrubbing), `live.py` (leases, live inboxes, claiming, wrapping, light config), `router.py` (pure routing), `wakes.py` (ledger, caps, coalescing), `heldback.py` (wakes a cap held back), `adapters.py` (the routine POST, notify-owner), `daemon.py`, `attach.py` (hooks), `launchd.py` (install), `listener_cli.py` (commands).  Files are written atomically with per-path locks (a thread lock plus `flock`).
- **The Operator's Zulip identity is the host's to provide.**  `OPERATOR_ZULIP_USER_ID` and `OPERATOR_ZULIP_EMAIL` name the Operator service bot, and the runtime reads them from the environment at call time:  no id is committed, because a production user id is private inventory (Kody review on AFC-473).  The user id has two sources, in this order:  the environment variable `OPERATOR_ZULIP_USER_ID` first, and the id the host pins in its own `listener.toml` under `[daemon] operator_user_id` second, the same place the owner's id is pinned.  A deployment with neither set has no id at all, and the runtime fails closed rather than guessing:  `operator_user_id(env, pinned)` in `scripts/simple_tools/dm_policy.py` resolves the two sources and returns `None`, and its consumer `operator_opened_dm` (and `check_new_dm` behind it) then refuses with the code `missing_operator_user_id`, whose message names the variable the host has to set.  That refusal is a deployment problem, not the DM rule saying no:  a seat that was answering inside a direct message Operator opened must never be told "you may not open a direct message".  The Mac host carries the two in the launchd definition and in each seat's MCP registration;  the hosted server host reads them from Infisical (`OPERATOR_ZULIP_USER_ID` and `OPERATOR_ZULIP_EMAIL` are in the loader's shared names).  A user id and an address are not credentials, so they may sit in a launchd definition, but they never belong in source.  Muster's read-only Operator service (`simple-chat muster-service`, `docs/muster-operator-zulip.md`) runs with only HOME and PATH, so it also reads the address from `[daemon] operator_email` in the same `listener.toml`, after the environment, and needs `owner_user_id` there too;  it fails closed when any of the three is missing.  The daemon's own voice uses the same pins:  when its environment names neither `OPERATOR_ZULIP_USER_ID` nor `OPERATOR_ZULIP_EMAIL`, it fills them at start from `[daemon] operator_user_id` and `operator_email` (the environment wins and is never replaced), so the Mac's LaunchAgent needs no `OPERATOR_ZULIP_*` names.  A reload applies a changed or removed pin that came from the file:  the Operator voice drops a client it had verified against the old pin and builds again at once.
- **Entry script:**  `scripts/simple-chat` re-runs itself with a Homebrew python3 when it finds itself on Python older than 3.11, so a GUI app or launchd that resolves the system 3.9 still works.
- **Single instance:**  `flock` on `~/.simple-tools/listener/daemon.lock` (it also holds the pid for `daemon reload` and `status`).
- **Lifecycle:**  a bad config never makes the daemon exit (which would re-register every queue every 30 seconds); it stays up, shows red in status and sends one notify-owner.  SIGTERM deletes its queues and kills the process group of every running wake child (several seats can wake at once), and a child that starts after the stop is killed at once.  SIGHUP re-reads the config.

**Which bots.**  Only seats with an enabled `[seat.X]` section in `listener.toml` get a queue (`enabled = false` keeps a seat listed and checked, but gives it no queue).  The daemon never lists every bot;  it reads exactly the listed seat's own `bot` keys from Infisical `/zulip` (`bot = "Grok-Build"` reads `GROK_BUILD_ZULIP_EMAIL`, `_KEY` and `_SITE`), fetching every seat's names in one call at start and holding them in memory only, or `<bot>-zuliprc` only from an explicit `SIMPLE_TOOLS_SECRETS_DIR`, and never `ZULIP_RC` or the environment triple, so seats cannot alias one bot.  On the server instance only, a seat may say `creds = "env"`.  It then reads its own named variables, `ZULIP_<CODE>_EMAIL` and `ZULIP_<CODE>_API_KEY` by default, with the site from `ZULIP_SITE`.  No two seats may share a variable, and none may use the generic triple.  The realm host is still enforced.  At connect it calls `GET /users/me`, checks that the email matches the credential, and refuses any bot whose role is not moderator (300) or member (400), or that reports `is_admin` or `is_owner` (decision 7).  It also refuses a key whose `users/me` is not the seat's own bot (the seat tag from its email must equal the seat), so a section cannot hold another seat's bot.  A refused seat shows red and is retried every 5 minutes.  Enabling a seat is a `listener.toml` edit followed by `daemon reload`.

**Queues.**  One `POST /register` per bot with `event_types=["message","update_message","user_topic","realm_user"]`, `apply_markdown=false` and no narrow.  Narrow terms are ANDed, so following the set of leased topics would need one queue per topic.

- `EventQueue` in `zulip.py` takes `event_types`, returns raw events (`poll_events`), keeps the register response, and records the last-event time (heartbeats included).  The CLI's `wait` and `listen` still register only `message`.
- The `GET /events` read timeout comes from `event_queue_longpoll_timeout_seconds` in the register response, plus 10 seconds.
- The register response seeds the user cache (`realm_users`) and the muted (1) and followed (3) topics (`user_topics`); `realm_user` and `user_topic` events keep them current.
- The client honors `Retry-After` on 429.  It does not read other rate-limit headers, and the design assumes no fixed limit.

`simple-chat listen` and `wait` stay for a seat that reads Zulip itself.

## 2. Routing

**Every channel (owner ruling, Sat, Oct 10, 2026):**  "I want bots to wake to any channel or DM" … "not just simple-tools or one other".  Routing has no channel filter:  a direct mention or a DM wakes from any channel the bot receives.  Zulip delivers a channel message only to a subscriber, so the daemon keeps each held seat's bot in every public channel:  at every connect it subscribes the bot to any public channel it is missing, and it registers for `stream` and `subscription` events so a newly created (or newly public) channel is joined at once and the seat's channel map stays current.  New subscriptions are set quiet (no desktop, push, email or sound notifications).  Private channels are never joined.  A failure is logged (`auto-subscribe-error`) and never stops the seat.  `[daemon] auto_subscribe = false` turns it off.  `scripts/simple_tools/subscribe_all.py` does the same once for every fleet bot, including seats no listener holds (BF bots, OPENCODE).  A typed `@**all**`, `@**channel**` or `@**stream**` wakes every seat that receives it, in any channel.

**State layout.**  Directories are mode 700 and files mode 600.

```
~/.simple-tools/
  listener.toml                          config (section 5)
  listener/  daemon.lock status.json pause.json loopguard.json notify.json probe.json
  logs/      listener.log(.1,.2,.3) launchd.out launchd.err hooks.log
  <SEAT>/cursor.json                     {"last_id": N}, flushed at most once a second, after appends
  <SEAT>/seat-inbox.jsonl                not for any lease; rotates at 1 MB or 7 days (.meta.json, .cursor.json)
  <SEAT>/owner-queue.jsonl               needs the owner; an entry expires once `inbox --local` shows it
  <SEAT>/wakes.jsonl                     wake ledger (section 3.4), kept 90 days
  <SEAT>/held-back.json                  messages the budget held back (section 3.5), one per message, kept until surfaced
  <SEAT>/leases/<lease_id>.json          lease_id = claude-code-<pid>-<pid start epoch>
  <SEAT>/live/<lease_id>/                inbox.jsonl delivered.json budget.json rewake.lock; removed 24 hours after the lease ends
  <SEAT>/<session8>/state.json           existing CLI cursors
  <SEAT>/inbox.json                      existing seat-wide mention cursor
```

**Identity.**  `daemon init` pins `owner_user_id` as the one user with role 100 (realm owner) and `is_bot` false.  It requires exactly one match, prints the id and email, and asks for confirmation (`--yes` skips the question).  It is never re-derived at runtime; `0` means not pinned, which treats nobody as the owner, runs no wakes and shows red.  It also pins `eligible_user_ids` (the bot user ids of CLAUDE, CODEX, AG, CURSOR, GROK, CLUTCH, FX, MM, MC, MA and JET), which is now only an optional extra:  see Eligible senders.  The user cache marks bots (message events carry no `is_bot`), and an unknown sender is treated as a bot.

**Eligible senders (owner ruling, Fri, Oct 9, 2026:  "everyone should be able to DM to wake anyone else or tag to wake anyone else").**  The owner, plus every fleet bot:  an active generic bot in the realm user list that the owner owns (`bot_owner_id`, the trust anchor:  a bot someone else creates under a fleet-looking email never counts, and with no owner pinned no bot counts), whose email maps (`seat_tag_for`, the same derivation the bot check uses) to a fleet tag.  The fleet tags are every seat the partition file lists, whatever its instance (Mac seats, the cloud seats MA, JET, GROK-WEB, WISE and ECHO, every `GB-*` bot, every `BF-*` role bot, GROK-BUILD), plus the fixed seats above.  The daemon computes the set at runtime from the user cache and the partition, refreshed on every partition check, so a new seat needs no re-init; `eligible_user_ids` adds pins on top.  Never eligible:  integration and webhook bots (Sentry, PagerDuty, Linear are Zulip incoming-webhook bots, and a webhook or embedded bot never counts whatever its email), unknown senders, API posts made with Jay's account, and a seat's own messages.  A peer wake is still peer data, never owner authority:  the woken seat screens it like any peer request (FLEET-PROTOCOL Precedence rule 3).

**Owner (decision 5).**  A message is the owner's only when `sender_id == owner_user_id` AND its `client` is a human Zulip app (`owner_clients`, default `website`, `ZulipMobile`, `ZulipFlutter`, `ZulipElectron`, `ZulipDesktop`; manual test 5 confirms the names).  A post made with Jay's account from any other client is not the owner and not eligible:  it never wakes, it is flagged `owner_api` wherever it lands, and it sends one notify-owner a day.  Zulip records the `client` the sending request reports (a `client` parameter or the User-Agent), so the check catches honest API use but cannot stop someone holding Jay's key from claiming a human client.  Owner priority is therefore a routing hint, never authority for a side effect; manual test 5 checks how a claimed client is recorded.

**OWNER topics (owner 2026-10-11, open-loops C6-2).**  A topic whose name starts `OWNER ` (any case, with or without Zulip's resolved check mark) is where a decision waits on the owner, and nothing a peer posts there wakes anyone.  A bot's direct mention, wildcard or `re=` reply is not an eligible message there (`router.Classes.owner_topic_peer`, wake block `owner_topic`):  it reaches no lease as an interrupt and no seat as a wake, and a seat that reads its inbox still sees it.  The one carve-out is the needs-owner notifier's directed note ("Jay replied"):  a message from CLAUDE's bot (the sender's email, which a message cannot copy) whose tag starts `[CLAUDE·needsown→`.  It is an ordinary mention, so it wakes the filer under the same stale rule.  The owner's own message there (a human client) wakes only the seats it mentions, and a seat that holds a lease on the topic still gets it as an interrupt.  A relayed "Jay said yes" from a peer therefore wakes nobody, and is never an answer.  An untagged post of the owner's there also wakes a seat that posted earlier in that topic, as that seat's most recent chat (section 2, Replies wake the chat they answer), so the owner's plain answer reaches the chat that asked.  A peer's untagged post there still wakes nobody.

**Leases.**  A session announces what it owns with `simple-chat attach`.  On Claude the hooks do it (section 3.1).  The lease is keyed by the platform process, not the session id, because `/clear` replaces `CLAUDE_CODE_SESSION_ID`.  SessionEnd with reason `clear` or `resume` therefore keeps the lease, and writing a lease under an id that ended earlier (a re-attach with the same `AGENT_SESSION`, a prompt after a real SessionEnd) first removes that id's old `ended.json` and `returned.json`, under the lease lock.

```json
{"seat":"CLAUDE","lease_id":"claude-code-90631-1791000000","platform":"claude-code","pid":90631,"pid_start":1791000000,
 "session_id":"<uuid, rewritten by the prompt hook>","cwd":"<absolute lane path from the hook>",
 "topics":[{"channel":"work-in-progress","topic":"AFC 18f61cf4 Zulip cutover","expires":null}],
 "mentions":true,"wake_capable":true,"permission_mode":null,"posted":[4801,4812],"wakes_seen":17,
 "last_prompt":1791000300,"heartbeat":1791000300}
```

- **Topics:**  `attach --topic T` adds a topic with no expiry.  `post` and `reply` add their topic with a 2-hour expiry, renewed by each post from that lease, and record the posted id in `posted`.  Presence topics (`presence_topics` in config:  #work-in-progress › `roll call` and `fleet`, #builds › `gates`, all of #alerts) are never auto-leased, and items in them are always passive.  `detach --topic T` or `--all` removes them.  Topic matching uses the CLI's `cursor_key()` casefold.
- **Liveness for `claude-code`:**  the pid is alive and its start time matches.  `claude agents --json` (cached 30 seconds) can only veto, on positive evidence:  the lease dies when the listing shows its pid with a kind other than interactive.  A pid missing from the listing, a listing in an unknown shape, or no such command leaves the pid and start-time checks to decide, so a format change cannot kill live sessions.  The daemon runs `claude agents --json` only with the pinned realpath, only when `test-wake` found its output usable (`agents_ok` in `wake-pin.json`), with stdin closed, and never while a pause covers the Claude seat; otherwise liveness rests on the pid and its start time alone.  An idle Desktop session runs no hook, so a heartbeat would wrongly expire it.  Other kinds (background, `-p`) never hold a lease.
- **Liveness for other platforms:**  the pid is alive, its start time matches, and the heartbeat is under 15 minutes old.  An `attach --wait` lease stays live for 2 minutes after its wait exits and is always `wake_capable: false`.  The lease id is `<platform>-s<sha256(AGENT_SESSION)[:12]>` when `AGENT_SESSION` is set, else `<platform>-<agent pid>-<start>`, where the agent pid is the nearest ancestor that is not a shell or wrapper; `attach` prints it, and `--lease` or `AGENT_LEASE` reuses it.
- **Mentions:**  `true` only for interactive `claude-code` leases, unless `attach --mentions` sets it.
- **Wake-capable:**  true only while an interrupt could start a turn now:  the lease is `claude-code`, the rewake watcher holds the lease's `rewake.lock`, the flag for the session's surface is true in `listener.toml` (`rewake_verified_cli` for a terminal, `rewake_verified_desktop` for the Desktop Code tab, from the lease's `entrypoint`;  the old `rewake_verified` sets both;  set each after manual test 1 on that surface), the seat is not paused, and the live budget has room.  Otherwise step 5 falls through to the seat inbox and the wake path.
- **Which lease gets a mention (router.py `route`, AFC-358 measured):**  a lease owns every topic it follows, and a lease follows a topic once it posts there (or `attach --topic`).  (1) If any live lease follows the message's topic, EVERY such lease gets the item, as an interrupt when the sender is eligible and the message is from the owner, a direct mention, or a reply to that lease's own post, else passive.  (2) Only when no lease follows the topic does a mention, DM or owner fleet wake go to ONE lease:  the wake-capable claude-code lease with the latest `(last_prompt, created)` and live-budget room, marked `delivered_to` in the seat inbox.  (3) With none, it stays in the seat inbox and the wake adapter runs.  For a seat with a `routine`, a mention, DM or owner fleet wake skips steps (1) and (2) and always takes step (3), because a session letter (`@**Claude** AB`) beats topic ownership and only the routine's router can honour it; the leases that follow the topic get such a message only as a passive item, never an interrupt (a presence topic, a roll call, stays passive for every seat and wakes nothing).  So when two sessions are live, the one that posted in a topic gets that topic's mentions;  an unleased topic goes to the most recently prompted wake-capable session, and a session that is not wake-capable (a Desktop tab while `rewake_verified_desktop` is false) is skipped in step 2 and sees such a mention only as a seat-inbox headline (and only if no other session was handed it).  Any wake-capable terminal session, even a throwaway one, takes step-2 mentions, so run rewake tests against a scratch `SIMPLE_TOOLS_STATE_DIR`.
- **Expiry:**  a dead lease's undelivered items go back to the seat inbox (those that qualify under step 6) and back through the wake decision.  A lease that is not wake-capable gets a 10-minute grace before a wake-worthy interrupt item is released as unowned; a released item is marked delivered in the lease, so it reaches the session or the wake, never both.  The release and the reap select and mark items under the same lock as `claim`.  A trigger released or returned from a lease never goes back to that lease:  the wake's takeover check skips it, so the wake runs instead of the item cycling between the lease and the seat inbox.  The reap re-reads the lease under its lock and leaves it alone if a hook wrote it again meanwhile, and honors a `returned.json` only when it is newer than the lease's `created`.
- **Topic renames:**  on `update_message` with a new `subject` (or channel) and `propagate_mode` `change_all`, leases and CLI cursors are rewritten.
- **Edits that tag a seat (owner, Oct 29 2026):**  "make sure edited messages wake anyone tagged."  A content edit whose new text tags the seat (its own `@**Name**`, or a fleet-wide `@all`, `@channel` or `@stream`, outside code and quotes) where the old text (`orig_content`) did not is fetched again for the seat's own flags and routed like a new message (`Daemon.route_edit`):  the same eligibility, owner-topic rule, leases, inbox and wake, with `edited: true` on the item.  The stale rule reads the edit's time, not the first post's.  A seat wakes at most once per message by edit, so a tag removed and added back never pages it twice, and a mention that was already there never wakes again.  An edit of a direct message, an edit that silences the mention (`@_**Name**`), a rendering-only edit (a link preview) and an edit made while the seat's queue was down (backfill starts at the cursor) wake nobody.  The owner's pause command and a registration answer are never carried out again on an edit.  Any other content-only edit is ignored and never delivered.

**Router steps**, for each `(seat, message)` pair.  One channel message arrives on every subscribed bot's queue, so dedupe is per seat.

1. Drop the message if its id is at or below the seat's backfill floor or in a 5,000-id in-memory ring.  Drop it if the topic is muted for this bot, unless it is `direct` or `dm`.
2. **Classify.**
   - `own`:  the sender is this seat's bot.
   - `owner`:  `sender_id == owner_user_id` and a human client (above).
   - `eligible`:  `owner`, or the sender is a fleet bot (Eligible senders, above) or in `eligible_user_ids`.  Webhook bots (Linear, Sentry, PagerDuty), API posts from Jay's account and unknown senders are never eligible.  GB bots, BF role bots, ECHO, WISE, GROK-WEB and Jet are eligible (owner 2026-10-09); their direct @-mentions and DMs wake.
   - `direct`:  the bot's `mentioned` flag is set AND the raw content outside code blocks, code spans and quotes contains `@**<bot full name>**` or `@**<name>|<id>**`.  The flag excludes code spans and quotes; the raw match excludes group mentions.
   - `broadcast_all` (a typed `@**all**`, `@**channel**` or `@**stream**` outside code, quotes and escapes, read from the raw text and not from Zulip's wildcard flags;  `@**everyone**` alone and `@**topic**` never count), `fleet` (a `broadcast_all` in #work-in-progress › `fleet`), `peer_broadcast` (an eligible fleet bot's `broadcast_all`, outside a DM),
     `wildcard` (the wildcard flags), `dm`, `wake_tag` (content starts with `[<ANY-SEAT>·wake`), `stale` (older than `stale_after`), `reply_to` (the numeric `re=` id in the first line, if any), `reply_to_chat` (an untagged post that answers one of this seat's chats, labelled `reply`, computed from the topic ledger: see [Replies wake the chat they answer](#replies-wake-the-chat-they-answer)).
3. **Own posts** go to other leases of the seat on that topic as passive `sibling` items, never to the poster (its `posted` list or its session tag).  They never wake and never enter the seat inbox.
4. **Leased topics.**  Append to every live lease on `(channel, topic)`, interrupt or passive (below).  Done.
5. **Mention-class items** (from an eligible sender:  `direct`, `dm`, a `broadcast_all` outside an OWNER topic, `reply_to_chat`, or the owner's `fleet`) in an unleased topic go to exactly one live, wake-capable `claude-code` lease with `mentions`:  the one with the latest owner prompt, then the newest.  They are delivered as interrupts and the seat-inbox copy is marked `delivered_to`.  No wake follows; a second responder would double-reply.  A seat with a `routine` (`wake = "http"`) never takes this hand-off, and a lease that follows the topic never takes its mention-class items either, neither when the message is routed (the topic's leases get a passive item only) nor at the daemon's takeover check before the wake runs: they go to the seat inbox and the wake, so the routine's router can pick the chat, because a session letter beats topic ownership.
6. **Otherwise** append to the seat inbox if `direct`, `dm`, `fleet`, `broadcast_all`, `owner`, `wildcard` or `reply_to_chat`, or if the topic is followed.  Other chatter is dropped; it stays readable with `simple-chat read`.
7. **Wake prefilter** (deterministic, zero tokens), for seat-inbox items only:

   | Message | Wake? |
   |---|---|
   | `owner` and (`direct`, `dm` or `broadcast_all`;  a `broadcast_all` outside an OWNER topic) | Yes, as `owner`.  Owner coalescing (5 seconds).  When `stale`, once per topic per day |
   | Eligible non-owner `direct` or `dm`, not `wake_tag`, not `stale` | Yes, as `peer` |
   | `peer_broadcast`, not in an OWNER topic, not `stale` | Yes, as `peer`, in any channel |
   | `reply_to_chat` (an eligible, fresh, untagged post, in a topic where this seat posted earlier, that is not a `wake_tag`, `route_tag` or no-wake post and not in a presence topic or a peer's in an OWNER topic) | Yes, as `peer`, or as `owner` for the owner's post (section 2, Replies wake the chat they answer) |
   | Sender not eligible (integration and webhook bots, non-fleet bots, API posts from the owner's account, unknown) | Never.  Inbox only |
   | `@**everyone**`, `@**topic**`, a silent mention, followed-topic chatter | No |
   | `wake_tag` (in a topic or a DM), non-owner `stale` | No.  Inbox only |
   | `own` (the seat's own post or DM) | Never |

8. Advance the cursor only after the append is flushed.  A message id that crashes the router 3 times is quarantined to the seat inbox.  A retry repeats only the steps that did not complete:  across the retries, a lease or seat-inbox append and the wake offer each happen at most once, and the loop guard counts a wake reply once, whichever step failed.

**Live classes** (step 4):

| Class | Members | Effect |
|---|---|---|
| `interrupt` | From an eligible sender:  an owner message, a `direct` mention, a message whose `reply_to` is in the lease's `posted` list, or an untagged reply to one of the seat's chats (`reply_to_chat`).  Never in a presence topic | May start a turn (section 3.1), within the live budget.  Over budget it is passive, with one throttle line |
| `passive` | Everything else:  sibling posts, peer chatter, status blocks, wake replies, presence topics, drafts | Appended only.  The next `prompt` hook shows one headline per topic (the daemon's `[owner]` mark first, then channel, topic, count, latest id and sender, with every name a quoted JSON string), never a body |

Owner messages raise priority, not authority.

### Replies wake the chat they answer

Chat A (seat S, header letter AA) tags seat T in a topic, T's chat answers in that topic without tagging anyone, and that answer wakes chat A (seat S, letter AA).  Any later post in the same topic counts, not only a Zulip quote-reply.

**The rule (`router.Classes.reply_to_chat`, label `reply`).** A post wakes seat S when seat S's bot posted EARLIER in the same channel topic (strictly earlier by message id) and the post:

- is eligible: the owner from a human client, or a fleet bot, and not S's own bot or another bot that signs as S (a chat is never woken by its own post);
- is fresh (not `stale`), is not a direct message and is not in a presence topic;
- tags nobody: no `→` list in its leading tag, no loud mention of anyone (`@**Name**`, `@**Name|id**`, a user group `@*name*`, the owner and every bot included) and no `@all`, `@channel`, `@stream` or `@everyone`.  A silent mention (`@_**Name**`) and a mention inside a code span, a code block or a quote tag nobody;
- is not a `·wake` reply, not a `·route` post, has no 👀 no-wake marker, and is not a peer's post in an OWNER topic.

**Which chat.**  The target letter is the header letter (`[CLAUDE: AA.1.S 📁AFC]` gives `AA`) of the MOST RECENT earlier post of S in the topic, except that an earlier post that tagged the sender's seat (a `→` list or a loud mention of the sender's bot) is preferred over a more recent one that did not, because the chat that called on the sender is the one the sender most likely answers.  The owner has no seat, so for an owner post it is the most recent.  When that post had no letter (a legacy `[CLAUDE·aaaa1111]` tag, or none) the wake carries no letter and the router falls back to the topic and recency, as for any wake without a letter.  The letter is read from a post's own header only when the header names the sender's own seat, and a token longer than 8 characters is not a letter.

**What it is.**  A wake like a direct mention, with the wake kind `owner` when the sender is the owner (a human client) and `peer` otherwise, so every rule after classification is the one a direct mention meets: the seat-inbox copy (`classes` carry `reply`, the row carries `reply_target_letter` and `reply_target_id`), the leases (a session that follows the topic gets an interrupt, a seat with a `routine` hands nothing to a session and goes to its router, any other seat's unleased topic goes to the one wake-capable session, a dead session's item is requeued), the muted-topic drop, the stale rule, the no-wake marker, the presence-topic rule, the coalescer and any cap the seat sets.  It is labelled so a wrong pick can be read back: the route log line (`decision.linked_by`, `decision.reply_target_letter`), the seat-inbox row and the wake ledger row (`linked_by: "reply"` and `reply_target_letter`, for the trigger the wake is about, the newest owner trigger when the owner is among them) all say it.

**Nothing throttles it.**  This class adds no budget, cap, spacing or loop guard.  A cap a seat has set holds it back like any peer wake.  Two bots that answer each other without tagging anyone keep waking each other's chats.

**The topic ledger (`TopicLedger` in `router.py`).**  The daemon keeps, per `(channel, topic)`, the most recent 40 posts as (message id, sender user id, sender seat, header letter, seats the post tagged), for at most 2,000 topics (least recently written out first).  It has no I/O, is thread-safe, and holds stream posts only: a direct message is never kept.  The daemon records every stream message it routes exactly once (deduplicated by message id, so the copies on every seat's queue, an edit's re-route and a retry change nothing), before the message is classified, and the classification reads only posts with an id below the message's own, so the order of the seats' queues never changes an answer.  The seat of a sender is the realm's answer (a fleet bot in the user list), never the message's, and the seats a post tagged are its `→` list and the fleet bots it mentions loudly by name.  A topic rename moves its posts with it.

**Limits, stated plainly.**

- Chats of the same seat share one bot, so they cannot be told apart by sender: a post by chat AB is the seat's own post and never wakes chat AA, and a reply that answers AA but follows a later post of AB is delivered to AB's letter (or to AA's, when AA's post tagged the sender).  The router and the chats sort it out from the letter and the topic.
- A restart empties the ledger (it is memory only).  The daemon does seed it, from the seat's OWN latest posts only, which is all the rule reads: at a seat's first connect of a run it reads one page of up to 200 of the seat's own newest posts (`SeatRunner.fetch`, newest first, one request, no paging) on the seat's own connect thread, records them and routes nothing.  A chat whose last post is older than that, or whose seed read failed (logged as `topic-ledger-seed-error`), is remembered again only when it posts again.  There is no per-topic history read on the routing path, because that would block the router on the network.
- A post that no seat's queue has delivered yet when a newer post is judged is missed for that one judgment (the seats' queues are not in step).
- A session that follows a topic is interrupted by every eligible untagged post in it, within the live budget, as for a direct mention.  A seat without a routine hands a reply to a session by recency, not by letter, because the router does not know a lease's letter; only a routine's router honours the letter.
- The Stop hook's continuation and `simple-chat inbox`'s mention headlines still read only `direct`, `dm` and `fleet` rows (`live.SEAT_MENTION_CLASSES`), so a reply row reaches a running session through the lease and the wake, and shows in the seat inbox, but does not itself continue a session at the end of its turn.
- The Operator's seat never gets one (a service seat holds no chat), and the hosted MCP Worker forwards only the body fields it knows, so it ignores `letter` and `linked_by`.

**To the router (`simple-tools-wake/1`).**  For a trigger that is a reply, the wake body carries the chat's letter in the optional `letter` field (left out when the post it answers had none) and `linked_by: "reply"`.  Both are additive: a body for a trigger with an explicit letter in its own text (`@**Seat** AB`) carries neither, because the router reads that letter from the text, and a receiver that ignores them still works.  The field table is in [eavesdropper-server.md](eavesdropper-server.md#the-routine-wake-http) and the router contract in [zulip-wake-routing.md](zulip-wake-routing.md).

## 3. Delivery and Wake

### 3.1 Live Claude Session (CLI and Desktop Code Tab)

**Chosen.**  Hooks for passive delivery and an `asyncRewake` hook for waking an idle session on both surfaces.  They ship as a local plugin, `plugins/simple-chat/` in AFC, with `.claude-plugin/marketplace.json` (marketplace `afc`) at the AFC root.  Install with `claude plugin marketplace add <the runtime checkout path> --scope user` and `claude plugin install simple-chat@afc --scope user`.  Every PR that touches the plugin bumps its `version`, and the install step runs `claude plugin update simple-chat@afc`.  `simple-chat status` prints the repo and installed versions.

**Scope.**  The hooks attach only when `CLAUDE_CODE_ENTRYPOINT` is `cli` or `claude-desktop` (test 1 confirms what `-p`, `--bg` and SDK runs report).  Anything else exits 0 without writing a lease unless `SIMPLE_TOOLS_ATTACH=1` is set.  A session a launcher started (`AGENT_LAUNCHER` or `AGENT_LAUNCH_SEAT` set) never attaches, even with `SIMPLE_TOOLS_ATTACH=1`, and `SIMPLE_TOOLS_ATTACH=0` turns the hooks off for any session.  The seat follows FLEET-PROTOCOL's seat precedence (`scripts/simple_tools/identity.py`):  `AGENT_SEAT`, else `[platform.claude-code] seat` in `listener.toml` (decision 6).  When neither resolves, the hook exits 0 and logs one line to `logs/hooks.log`.  A seat the partition does not give to the `mac` instance (a BotFleet bot, a cloud seat, an unlisted seat) gets no lease:  the session-start hook says so in one line, such as "seat BF-PLUMBER is not served by the Mac listener", and the other hooks stay silent.  The pid comes from `CLAUDE_PID`, which hooks and Bash already receive (else the hook's parent pid).

**Fast path.**  The entry script dispatches `attach` and `detach` before `cli` is imported.  `attach.py` and `live.py` import only json, os, time, fcntl, threading, re, unicodedata and tomllib; argparse loads only for the forms that are not hooks, and subprocess only when a lease is first written (`ps` for the start time).  The import costs about 16 ms here, and a test checks that no heavy module loads.  Importing the full CLI costs 0.3 to 0.45 seconds, too much for every prompt and Stop.

`plugins/simple-chat/hooks/hooks.json` (no `PreToolUse`; exact async keys per the hooks reference, test 1):
```json
{"hooks":{
 "SessionStart":[{"hooks":[{"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --hook session-start","timeout":5},
   {"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --rewake","asyncRewake":true,"timeout":86400}]}],
 "UserPromptSubmit":[{"hooks":[{"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --hook prompt","timeout":5},
   {"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --rewake","asyncRewake":true,"timeout":86400}]}],
 "Stop":[{"hooks":[{"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --hook stop","timeout":5},
   {"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --rewake","asyncRewake":true,"timeout":86400}]}],
 "SessionEnd":[{"hooks":[{"type":"command","command":"\"$HOME/.local/bin/simple-chat\" attach --hook session-end","timeout":5}]}]}}
```

The commands use the installed symlink by absolute path, so a GUI app's short `PATH` cannot miss it.

| Path | What it does | Token cost |
|---|---|---|
| `session-start` | Writes the lease (a reused pid with another start time gets a new lease).  `permission_mode` stays unknown, because SessionStart input has none.  Returns counts only:  seat inbox, owner queue, and wake outcomes since the lease's `wakes_seen`.  Says nothing on resume, compact or clear unless a count changed | Rides the first turn |
| `prompt` | Rewrites `session_id`, `permission_mode` and the heartbeat, and `last_prompt` unless the prompt is a rewake delivery.  Writes the lease again if it was ended (clearing the old end markers).  With rewake verified and no pause, claims pending interrupt bodies (1,500 characters).  Adds passive headlines for the rest, and headlines for NEW seat-inbox mentions and DMs (direct, DM or fleet wake, undelivered, not stale, not the seat's own) past the lease's `inbox_seen` cursor (AFC-358;  headlines only, never a body).  Prints nothing when nothing is pending | Rides a turn already happening |
| `stop` | Refreshes `permission_mode` and the heartbeat, and records whether `background_tasks` lists the rewake watcher.  When an eligible sender's mention or DM reached the seat inbox during the turn (past `inbox_seen`), it continues the turn once with `{"decision": "block", "reason": <headline>}` (AFC-358), which covers sessions where rewake is off, such as the Desktop tab.  Once per message (the cursor moves), never on a Stop that already follows a continuation (`stop_hook_active`), only for the most recently prompted live session of the seat, at most 3 an hour a lease, and never while paused.  Mentions it does not continue for get their headline at the next prompt | 0 until it continues, then one short turn |
| `--rewake` | One per lease (`rewake.lock`; duplicates exit 0 at once).  Exits 0 at once unless the flag for this session's surface (`CLAUDE_CODE_ENTRYPOINT` `cli` or `claude-desktop`) is true.  Polls the lease inbox once a second and coalesces for 3 seconds.  When interrupt items are pending and the live budget allows, claims them and exits 2 with the wrapped batch on stderr, which wakes the session.  Exits 0 when the lease or the Claude process goes, or at its timeout.  Re-armed on every prompt and Stop | One turn per batch, zero while silent |
| `session-end` | For reason `clear` or `resume` the process goes on, so the lease stays and the next SessionStart rewrites `session_id`.  Otherwise removes the lease and marks the live directory ended; the daemon returns undelivered items to the seat inbox when it reaps it | 0 |

**Claiming.**  The rewake hook, the prompt hook and `attach --drain` share one `claim(lease, max_chars)`:  take the lock, select items, advance `delivered.json` before printing, release.  Delivery into model context is at most once; `inbox.jsonl` stays the durable record, and `attach --drain --replay N` reprints the last N delivered items.  Caps:  rewake 1,500 characters and 400 per message; drain 6,000 and 1,500 per message.  Over a cap the newest items are kept and the line says `N older omitted, use simple-chat read --since ID`.  Items older than `stale_after` are counted, not printed.  Each batch has one short header line, then one daemon line naming the owner items (`Owner items (daemon-checked: the owner's user id from a human Zulip app): <ids>`, or `none`), then the block.  Inside the block each item is exactly one JSON object (metadata and `body`), so a body cannot forge a metadata line, and only the daemon line outside the block marks owner items.  It repeats no policy text.

**No taint guard (decision 8).**  There is no `PreToolUse` hook, no `taint.json` and no tool lockdown in live sessions.  What protects a live session is the untrusted wrapping with nonce markers (section 4), the caps, the live budget and the live loop guard, plus the fleet rule that Zulip content is data.  The CLI's `post` and `reply` refuse text that matches the secret scanner.

**Live budget**, per lease:  peer interrupts get 6 turns an hour, 30 a day, and at most 1 per topic per 5 minutes.  Owner interrupts count separately:  20 a day and no per-topic spacing, so a follow-up from the owner is never held back, and owner turns never space peer turns.  Over budget, the topic turns passive, one throttle line is delivered, and one notify-owner goes out per day; the routine per-topic spacing sends neither (the item still shows as a headline).  After 3 interrupt turns in a topic with no owner message in between, the topic turns passive until one arrives.  Only an owner Zulip message resets this; an owner-typed prompt does not, because no hook field yet tells an owner-typed prompt from a rewake, scheduled-task or subagent prompt (manual test 1 looks for one).

**Other platforms.**  `simple-chat attach --wait` is the platform-neutral form of `minimax-slack-alert.py`:  a background command the session owns that blocks for one batch, prints it wrapped and exits 0 (4 on timeout).  `attach --drain` prints what is waiting.

### 3.2 The Wake

A seat has one of two shapes, and `SeatConfig.mode` names it.

| Mode | When | What a wake-worthy message does |
|---|---|---|
| `routine` | The seat has a `routine` table | The daemon sends one signed POST (`simple-tools-wake/1`) to the seat's router, which picks the chat, delivers and wakes it ([zulip-wake-routing.md](zulip-wake-routing.md)).  A single-threaded seat's routine is its own endpoint, with no chat to pick |
| `capture` | No `routine` | The message stays in the seat inbox, and a live session reads it there |

The body carries the trigger's ids, channel, topic and stream id or DM members, the sender, the daemon's owner flag, a 2,000-character excerpt inside the untrusted markers, a Zulip link, the seat and `dm`, and for a reply `letter` and `linked_by`.  The URL and key come from the environment variables the `routine` block names, read once at start, so a new or rotated value needs a restart.  Auth is a plain header, Bearer, or a hex HMAC-SHA256 of the raw body.  A 2xx is accepted;  a 5xx or a network failure is retried 3 times with backoff;  a 4xx or a redirect never is.  A 2xx is acceptance, not a delivery:  the router's final receipt says what happened.  The URL, query, key and signature are never logged ([eavesdropper-server.md](eavesdropper-server.md#the-routine-wake-http)).

A seat with a routine never hands a mention-class message to a live session (section 2, step 5):  it goes to the router, because a session letter beats topic ownership and only the router can honour it.

**notify-owner** writes the owner queue, and on a Mac also shows a banner through `osascript` with a list argv.  Seat, sender and topic are attacker-controlled, so they are control-stripped and cut to 120 characters first.  It never shows a body.  Each kind notifies at most once a day unless it is per event (`listener/notify.json`).

### 3.3 The Operator's Voice

**The rule:  "The operator should never be answering on behalf of a platform."**  The Operator never posts a wake's reply, an owner ack, a route page or a quota notice, for any seat.  It asks nobody a clarifying question, and it never DMs anyone:  anything that would be a DM goes in Side-Chats.  `Daemon.post` is a refusal:  it logs `post-refused` with the reason `operator_never_answers`, puts that reason on the wake's ledger row as `post_error`, sends nothing and keeps no text.  `test_operator_never_answers.py` fails the build if code builds an `[OPERATOR·wake]` reply, an `[OPERATOR·route→SEAT]` page or an owner ack, or if a new function sends as the Operator.

When an agent's Zulip identity is used, it is for something that agent thought about and said.  Text the daemon composes never goes out under a seat's bot:  it goes out as the pinned Operator bot.

What the code still sends as the Operator:

| Post | Where the code sends it |
| --- | --- |
| The escalation note (`dm_owner`) | A DM to the owner, tagged `[OPERATOR·note]` |
| The `@all` reminder (`_run_broadcast_audit`) | A DM to the owner, tagged `[OPERATOR·note]` |
| The held-wake digest (`_held_alert`, `_held_alert_edit`) | `#alerts`, one standing post edited in place |
| The candidate list (`ask_operator_for_candidates`, `operator_candidates.py`) | A DM to the sender of a tagged address, with the owner or an allowed user |
| The registration question (`operator_registration_ask.py`) | The registering chat's own topic |

The DMs, the candidate list and the registration question are what the rule above removes (section 9).

**One choke point.**  `Daemon._operator_send` (and `_operator_edit`) is the only place the daemon writes composed text to Zulip.  It secret-scans the content, takes the next 3-second slot, and posts with the Operator client from `operator_post.OperatorVoice`.  No site calls `runner.client.post` or `.patch` any more, and a test fails the build if one comes back.  Which functions may call it is pinned too (`test_operator_never_answers.py`): `dm_owner`, `_run_broadcast_audit_body` and `_held_alert`, so a new sender is a deliberate change to that list and never an accident.

**The tag says OPERATOR, not the seat (owner ruling, Oct 30 2026).**  The Operator's own notes read `[OPERATOR·note] re=<trigger id>`: the sender line and the tag both say Operator, and the seat the note is about is in a `Seat:` line of the note and in the wake ledger row (`seat`, `wake_id`, `trigger_ids`).  The router and the loop guard still match any `[WORD·wake]` or `[WORD·route` tag on a post another bot wrote, so nothing there changed; the Operator posts neither tag.

**The Operator client** is built on first use, the way `operator_registration_ask.send_location_question` builds its own: the credential comes from Fleet-OPS `/zulip_operator` through `service_identity.operator_credentials`, and `users/me` has to be the pinned Operator bot owned by the pinned owner (`service_identity.operator_bot`, from `OPERATOR_ZULIP_USER_ID` and `OPERATOR_ZULIP_EMAIL`) before anything is sent.  It is cached, a rejected credential (401 or 403, on a post or an edit) drops it, and so does a changed owner pin.  A build that fails is remembered for two minutes, so a vault outage costs one attempt per window.  A build reads the vault and asks Zulip `users/me`, so it never runs under the client's lock: it is single flight (the first caller builds, the others join it) and only the cached state is guarded.  **The router thread never waits for a build.**  The digest and an edit of it ask with `wait=False`: with no client ready they are skipped that time (the digest's window stays unspent), the build goes on in the background, and the next ask finds it.  `Daemon.run` starts that build at start (`OperatorVoice.warm`).  The Mac needs no `[seat.OPERATOR]` section for this.  The client carries the owner pin, so the owner-in-the-conversation guard (AFC-469) applies to it like to any bot: every direct message it sends has the owner in it, and the one-to-one status exemption (`operator_status_dm`) is not used.  **Its state is published.**  `status.json` carries `operator_voice`: `available` (true or false once a build has finished, null before the first), `code` (the failure's reason token, such as `operator_unavailable`, `operator_owner_not_pinned` or `operator_credential_rejected`, never a reason sentence and never a value; null when the Operator can speak) and `since` (when that answer began, ISO-8601 UTC; a failure retried every two minutes keeps its first time).  A status reader uses it to tell a listener that is up with a dead Operator voice from a healthy one, which the container's own health cannot.

**No fallback.**  With no Operator (the vault cannot be read, the credential is rejected, the identity is not the pinned one, the owner is not pinned) the post is not made.  The daemon logs `operator-voice-unavailable` once per window with the reason and `operator-post-refused` for each post it dropped, with the `site`: `owner-dm`, `broadcast-audit`, `held-alert`, `held-alert-edit` or `wake-preflight`.  A wake's reply is not one of them: it is refused by the rule (`post-refused`, reason `operator_never_answers`) whether or not the Operator could post, and the row is `done` with `post_error`.  The seat's bot is never tried instead.

**What does not change.**  A seat's own words, typed by that agent through its own tools (`simple-chat`, the MCP tools), still go out as the seat: the rule is about text the daemon composes.  `daemon probe` (a diagnostic a person runs) and the inbox delivery (subscriptions and read flags, no text) are not wake posts and are untouched.  The router and the loop guard still read a `[WORD·wake]` tag on anyone else's post (a `·wake` post never wakes anyone); the Operator just never writes one.

### 3.4 Ledger and Reporting

`<SEAT>/wakes.jsonl` is written before anything it guards:  a `queued` line (trigger ids, due time) before the cursor advances, an `accepted` line when the job enters the FIFO, a `started` line before the POST, and `done` or `failed` after it.  `held_back` (a cap or a full FIFO, section 3.5), `dropped` (the pause, the loop guard when it is on, staleness, a routine that is not ready) and `skipped` (a session took over) end a wake that never ran;  a held-back wake later gets one more row, `surfaced`, `expired` or `evicted`.  On restart, queued and accepted wakes are reloaded and every check runs again, and a non-owner wake whose newest trigger is older than `stale_after` is dropped as `stale`.  A `started` with no outcome is marked failed and never re-run.  A wake whose trigger is an untagged reply carries `linked_by: "reply"` and `reply_target_letter` on every row, so a wrong pick can be read back.

A `done` row means the router accepted the wake.  It is not a delivery:  the router's receipt is (section 8).

A guard drop is a row too:  a wake the loop guard or the stale-once rule closes writes a `dropped` row with `reason` `loop_guard` or `stale_once`, the trigger id and `guard_count`.  `status.json` carries a top-level `loop_guard` list of the topics it holds.  `simple-chat wakes` lists the ledger.

### 3.5 Held-Back Wakes (Every Seat)

A wake a cap refuses is held back instead of dropped, so a message is never lost to a cap.  The caps have no default, so this happens only for a seat that sets one, or when the FIFO of 5 is full.  Code:  `scripts/simple_tools/heldback.py` and the daemon.

**What is held back.**  Exactly the budget refusals, whether a budget refused the wake when its quiet window ended or again just before it ran.  Every other refusal stays a plain `dropped`, as before.

| Becomes | Reasons |
|---|---|
| `held_back` | `wakes_per_hour`, `wakes_per_day`, `per_topic_per_hour`, `owner_per_day`, `owner_per_topic_per_hour`, `usd_per_day`, and `overflow` (the FIFO of 5 was full) |
| `dropped`, as before | `owner_not_pinned`, `seat_refused`, `paused`, `inbox_only`, `routine_not_configured`, `routine_url_refused`, `routine_key_refused`, `loop_guard`, `stale` |
| Never in the ledger | the `wake-blocked` log lines (`loop_guard`, `stale_once`) and router skips (an ineligible sender, a duplicate, a seat's own post) |

**Which seats.**  A seat with a `routine` holds back every cap refusal and overflow, lists them in band as `held_back` in the wake body ([eavesdropper-server.md](eavesdropper-server.md#the-routine-wake-http)), and gets a catch-up wake.  A seat that captures only never wakes, so nothing is held back for it.

**The record.**  `<SEAT>/held-back.json` (mode 600) holds one record per held-back message (AFC-253, Sun, Oct 11:  every id a coalesced wake stood for, never only its representative):  the message id, which is also the reference to its seat-inbox row;  the owner flag and topic key;  `dm`;  the escaped display copies of channel, topic and sender (at most 100 characters each);  the stream id;  the Zulip link (left out when over 200 characters, never cut);  the reason;  and the time.  Never a message body.  The record is written before the ledger's `held_back` row, so a crash between the two loses nothing (the wake is then still queued or accepted and is checked again after the restart), and the file survives a restart like the ledger.  A message held back twice (a requeued trigger, or a catch-up a budget refused again) stays one record that remembers both wakes.  At most `max` records (200) keep their names;  past that the oldest move to an `overflow` tier of compact entries (id, reason, time, DM flag and what a catch-up needs), which are still listed by id.  Only past `overflow_max` (1,000) is an id lost:  it gets an `evicted` ledger row, the owner is told at once (`held-back-lost`, with the ids), and the `lost` counter keeps it in every count until a delivered wake reports it;  no timer clears it.  A record expires (an `expired` row, no wake) only when `ttl_hours` (24) have passed **and** an owner digest that was actually shown (a Mac banner) named it.  The server posts to `#alerts` instead ([AFC-257](eavesdropper-server.md#the-held-back-digest-on-this-instance)), which is not the same promise, so there nothing expires unsurfaced.  A wake's closing row (`surfaced`, `expired` or `evicted`) is written once the last message it held has left the file, and names the ids that left with it (`message_ids`).  A file from before AFC-253 is migrated on read:  each coalesced id becomes its own record, and the old `evicted` counter becomes `lost`.

**Surfaced in band.**  The next wake that runs for the seat carries the count (every record and overflow entry but the wake's own triggers, plus `lost`) and the **oldest** `items_in_wake` (20) as metadata only, overflow first, so every delivered wake moves the backlog forward and newer holds never starve older ones (an overflow entry is listed with `null` channel, topic and stream id and `""` sender and link):  `message_id`, `dm`, `channel`, `topic`, `stream_id`, `sender_full_name`, `zulip_link`, `reason` and `at`.  They are marked surfaced (a `surfaced` ledger row naming the wake in `by`) only after that wake reached the seat:  for `http`, a 2xx, and from the hosted MCP Worker only an answer that says it delivered (`delivered` of at least 1;  its 202 `no_subscriber`, `channel_refused`, `rejected`, `gone`, `not_live`, `paused` and `disabled`, and a `duplicate`, surface nothing).  A wake's own triggers surface with it, and so does a trigger handed to a live session.  Records held back while a wake was out, and records it counted but did not list, stay for the next one.

**Catch-up.**  When a seat with a routine has held-back records, nothing queued, waiting or running, and room in its budget again, the daemon starts one catch-up wake.  Its one trigger is the newest record (then overflow entry) that can be one (its topic not loop-guarded, its own budget open, and not refused before), rebuilt from the seat inbox:  the `http` body gets the real excerpt and `reply_to`.  The rest ride along in band.  Each candidate gets the checks a wake gets when its quiet window ends:  the kill switch, a routine that is not ready, the loop guard and every cap.  The catch-up then goes through the FIFO, is counted and is checked again before it runs like any wake, so it never adds a wake the budgets would not allow;  if a budget closed in between, it is held back again, never run.  The stale rule does not apply to it (its `trigger_ts` is empty):  a held-back message is owed until it surfaces.  A catch-up that surfaces nothing (the routine refused it, or the Worker said nobody got it) waits 15 minutes before the next, doubling to at most 4 hours, and anything surfacing resets the wait.  A record whose catch-up the Worker answered `channel_refused`, or whose trigger can no longer be found, is never a catch-up trigger again, but stays listed.  A paused seat, a disabled seat (it has no queue) and a seat with `catch_up = false` get no catch-up.  Every ledger row of a catch-up carries `catch_up: true`.

**Owner digest.**  At most one per seat per `owner_digest_minutes` (60), and only when messages were held back since the last one:  the count, the reasons, the overflow and lost counts, the newest three links and every new id.  Only a digest that was shown (notify-owner returned true with banners on) lets the entries it named expire.  It goes through notify-owner:  a banner and the owner queue on the Mac, the owner queue only on the server.  On the server a second, instance-wide digest posts to `#alerts > held-back wakes` ([AFC-257](eavesdropper-server.md#the-held-back-digest-on-this-instance)):  one standing message for every seat, edited in place at most once an hour and edited to an all-clear when the holds clear (AFC-569), on any hold rather than only an eviction, and it does not mark anything `told`.  It replaces the once-a-day notice per limit that a budget drop used to send.

**Config**, per seat, with the defaults:  `held_back = { max = 200, overflow_max = 1000, ttl_hours = 24, items_in_wake = 20, owner_digest_minutes = 60, catch_up = true }`.  `catch_up` defaults to `[daemon] held_back_catch_up` (true), applies only to a seat with a `routine`, and is the per-seat opt-out.  `owner_digest_minutes = 0` turns the digest off.  `max` is 1 to 1,000, `overflow_max` 0 to 5,000, `ttl_hours` 1 to 168, `items_in_wake` 0 to 20 (the Worker's cap) and `owner_digest_minutes` 0 or 15 to 1,440.  A bad value is an error like a bad budget, and the seat gets no queue.  None of these changes a budget.

**Accounting.**  `simple-chat wakes` shows each wake's state (`held_back`, `surfaced` with `by`, `expired`, `evicted`, `dropped`), marks catch-ups, and ends with the seat's held-back count, oldest age and reasons.  `simple-chat status` prints `held back N (oldest ...; reasons; M in overflow; L more lost past the caps)` under a seat that has any, and `status --json` carries the counts and lifetime totals.  `started`, `done` and `failed` rows record how many held-back wakes they carried (`held_back`), and an `http` `done` row records whether they surfaced (`surfaced`, plus the Worker's `routine_delivered` and `routine_outcome` when the routine is the Worker).

## 4. Efficiency and Safety

| Mechanism | Rule |
|---|---|
| Coalescing | A wake-worthy item opens a 20-second quiet window per `(seat, topic)`, extended by each new item up to 90 seconds.  Owner items wait 5 seconds, and a peer item never delays an owner wake |
| Wake caps per seat | Five count caps, none with a default:  non-owner `wakes_per_hour`, `wakes_per_day` and `per_topic_per_hour`, owner `owner_per_day` and `owner_per_topic_per_hour`.  Unset is no limit, a positive number is a cap and `0` pauses wakes;  Muster edits them.  A day is a rolling 24 hours.  Over a cap, the wake is held back, not dropped (section 3.5) |
| Loop guard | Off:  `[daemon] wake_loop_prevention = false`.  With the key absent the code's default is on:  after 3 `·wake` replies in a topic with no owner post in between, the topic stops waking, and a DM thread without the owner gets a rolling 6-hour window.  A `·wake` tag never wakes any seat, whatever the setting, so forging one can only suppress a wake |
| Dedupe | Per seat by cursor plus ring.  Per lease by `claim`.  Per wake by the ledger |
| Backfill | Register the queue first, backfill, route the backfill in id order, then read the events (the queue buffered them).  `is:dm`, `is:mentioned` and the owner's posts are paged from the cursor until exhausted.  Each leased or followed topic is fetched by its own narrow, newest first, capped at 200 with a gap marker.  Unleased chatter is never fetched.  Queues register in parallel with jitter; backfill is serialized across bots |
| Untrusted wrapping | Bodies sit between nonce markers, one JSON object per item.  Text is NFKC-normalized and stripped of format characters, marker text (any case, any separator) becomes `[marker removed]`, control characters become `\xNN`, U+2028 and U+2029 become `\u2028` and `\u2029`, and channel, topic and sender names are escaped onto one line and cut.  Outside the block, names in headlines and in the wake header are quoted JSON strings, and only daemon lines (the `[owner]` headline mark, the owner-items line, the wake header's owner ids) say which items are the owner's |
| Kill switch | `simple-chat daemon pause [--seat S] [--wakes-only]` stops wakes and live interrupts (capture continues); `resume` lifts it.  A DM from the owner saying `simple-chat pause` pauses every seat but never resumes. |
| Health | Every queue sees a heartbeat about every 50 seconds.  No event for 180 seconds means a dead queue:  re-register and backfill.  Down for 30 minutes:  one notify-owner and red in status.  The Slack relay's `/health` said 200 while delivery was dead for weeks |
| Sentry heartbeat | The daemon checks in to a Sentry cron monitor about every 5 minutes, from its own tick, and silence opens an issue.  See [Sentry Heartbeat](#sentry-heartbeat) |
| Probe | `simple-chat status --probe --seat S` posts in #sandbox › `listener probe` and passes when the daemon routes that message id within 30 seconds.  The seat's bot must be subscribed to #sandbox.  On demand only |
| Network and sleep | Back off 5, 30, 60, then 120 seconds.  A wall-clock jump over 120 seconds beyond monotonic time forces re-register and backfill.  Backfilled messages older than `stale_after` (120 minutes) wake only the owner, once per topic |
| Logging | `logs/listener.log` holds JSON lines with ids, seats, topics, senders, decisions and costs, never bodies or keys.  Adapter output is logged only as length and SHA-256.  `sys.excepthook` and `threading.excepthook` scrub every loaded key and its base64 form.  Rotates at 5 MB, 3 files |

### Sentry Heartbeat

Added Sat, Oct 10 (CLAUDE, AFC #441).  Owner ask:  the listener should report that it is running, on the Mac and on Coolify.  The code is `scripts/simple_tools/heartbeat.py`, called from the daemon's tick.  It adds no LaunchAgent, cron row, pm2 job or process, and uses no SDK (standard library HTTP).

- **Where to see it.**  Sentry org `simple-with-us` (https://simple-with-us.sentry.io), project `fleet-infra`, **Crons**.  One monitor per instance:  `operator-mac` and `operator-server`.  The first check-in creates the monitor (`monitor_config` upsert), environment `production`.
- **What it sends.**  A check-in every 5 minutes:  `ok` when healthy, `error` when degraded.  The monitor is an interval schedule of 5 minutes with a 10-minute margin and a failure threshold of 2, so a listener that goes silent (crashed, host off, restart loop) opens a Sentry issue after two missed intervals, about 20 minutes.  An `ok` after that resolves it.
- **Degraded means** any of:  an enabled seat is red (credentials refused, or its queue down for 30 minutes), `owner_user_id` is not pinned, or the config has errors.  When a degraded state lasts two beats in a row, that second request also carries one warning event (once per distinct problem, so a seat that has been down 31, then 36 minutes is one problem), grouped into one issue per instance (`simple-tools-listener / <instance> / degraded`), whose message names the reasons.  The reasons come from the same status the daemon writes to `status.json`, scrubbed.
- **The DSN** is the fleet-infra project DSN, the fleet-standard name `SENTRY_FLEET_DSN`.  `SIMPLE_TOOLS_SENTRY_DSN` wins when both are set.  Mac:  read from the environment, else `fleet-secrets get SENTRY_FLEET_DSN --path /simple-tools` (Infisical Fleet-OPS;  AFC-359).  Server:  Infisical `prod` `/zulip`, loaded at start by `server/infisical_env.py`, which allowlists exactly these two names.  A DSN change on the server needs a restart;  on the Mac it is read at every beat, so it needs none.  There is no third source:  the environment and the approved store are the only two, because a caller-named file picks the secret rather than the store, so the env-file override was removed on Oct 22 2026 (Kody review on AFC-473).  With neither source the DSN is empty, the heartbeat stays off, and the log says so once.
- **Off and tuning.**  No DSN means the heartbeat is off and the log says so once (`sentry-heartbeat-off`).  `SIMPLE_TOOLS_SENTRY_HEARTBEAT=off` turns it off on purpose.  `SIMPLE_TOOLS_SENTRY_ENVIRONMENT` overrides `production`.
- **Safety.**  The DSN and its key are scrubbed like a bot key and never reach `listener.log`, `status.json` or an error.  A send runs on its own thread (timeout 10 seconds), so Sentry being slow cannot stall routing.  A failure backs off 30 seconds, doubling to the 5-minute interval, and logs `sentry-heartbeat-failed` at most once every 30 minutes (the error is an HTTP status or an exception class name, never the URL).  `sentry-heartbeat-ok` is logged on the first success and on recovery.
- **Usage Monitor.**  The Mac needs nothing more:  `com.jays.mac-server-watchdog` already posts the Mac's launchd job list (every `com.jay.*` label, including `com.jay.operator`) to Usage Monitor's `POST /api/ingest/mac-heartbeat` every 120 seconds, and the Mac health card shows it under Launchd Background Daemons.  That endpoint accepts only the `mac-host` producer's Mac host payload, so the Coolify instance has no ingest endpoint there.  Reporting the server to Usage Monitor would need a new producer and route in the Usage-Monitor repo;  the Sentry monitor covers it.  `admin.jays.services` (`scripts/admin-panel`) has no ingest endpoint either.
- **Tests.**  `scripts/simple_tools/tests/test_heartbeat.py` runs the heartbeat against a fake Sentry ingest server on loopback:  payload, interval, degraded to `error`, the DSN never logged, backoff and its log rate limit, no DSN, a slow send.

## 8. After The Router Takes A Wake

The pick is in [zulip-wake-routing.md](zulip-wake-routing.md).  What follows the pick is in `scripts/simple_tools/wake_router.py` and, for Claude, `scripts/simple_tools/claude_wake.py`.

**A 202 or a queue receipt is not proof of a wake.**  The router answers 202 once the wake is on disk, and a 200 with the record only once it has a final receipt.  The listener treats any 2xx as accepted and never retries one, so its `done` row means the router took the wake.  The router keeps one final receipt per wake, in `wakes.jsonl` and at `GET /receipt/<id>`:  `status` is `delivered` (`delivered` true with proof, or null when handed over with none), `dead` (ended without a delivery, or interrupted, when `delivered` is null because nobody knows), `held` (picked, and not delivered because delivery is off) or `test`.  The router, not the listener, retries a failed delivery, up to `max_attempts`.

**Deliver and wake.**  Before each delivery the router asks the registry again;  a letter that no longer holds that session at the same generation ends a wake addressed to it with `target-released`.  For Claude, a chat a live process holds gets the wake on its inbox socket, and a chat no process holds is resumed with `claude --resume <id> -p` in its own folder under a per-session lock.  The resumed chat is the picked chat itself:  no separate model answers.

**Chats on the Mac.**  The router on the server reaches the Mac with one fixed command over ssh, `simple-chat wake-deliver`, with the wake as JSON on stdin.  The Mac process only delivers:  it does not listen and it does not pick.  The request names the `platform` (looked up in a fixed table;  an unknown one is refused), the `target` and the `wake`.  A short `true` over ssh goes first, so a sleeping Mac is `unreachable` and the wake waits.  The Mac asks the registry again before it delivers, and its answer repeats `wake_id`, `session_id` and `generation`;  an answer with other ids is final.  The router's ssh key can be limited to the forced command `simple-chat wake-ssh-gate`, which allows only those two commands.

**Settings.**  Infisical holds the router's settings, read through `fleet_knobs` by `scripts/simple_tools/wake_settings.py`:  at startup, then in a background refresh and on `SIGHUP`, keeping what it runs on when a refresh fails.  Muster's Controls tab shows and changes them.  Delivery runs for a seat only when `WAKE_ROUTER_DELIVERY_ENABLED` is true (default false) and `WAKE_ROUTER_DELIVERY_SEATS` (default empty) names it.  The others are `WAKE_ROUTER_WORKERS`, `_MAX_DELIVERIES`, `_MAX_ATTEMPTS`, `_RETRY_BACKOFF`, `_BUSY_RETRY_SECONDS`, `_UNREACHABLE_RETRY_SECONDS`, `_MAX_AGE_SECONDS`, `_SHUTDOWN_WAIT_SECONDS`, `_RESUME_TIMEOUT_SECONDS`, `_CONFIRM_SECONDS`, `_SETTINGS_REFRESH_SECONDS` and `_MAC_SSH`, listed with their defaults in `INFISICAL.md`.  A local `<state>/config.json` can only narrow them, apart from `local_host` and `claude_bin`, which are facts about one host.

**Test Wake.**  A body with `"test": true` is a dry run through the router.  The router answers at once with the whole pick and its link note, writes a receipt marked as a test, delivers nothing, reserves no id and never calls the decider.

## 9. Not Yet In The Code
