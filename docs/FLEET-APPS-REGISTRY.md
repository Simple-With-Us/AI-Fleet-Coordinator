## 4. Standing Rules & Standards

### 1. Where The Truth Lives


- **SRC-1 (App Store Connect is the source of truth for what actually exists.)**: appleId, bundleId, SKU, app state, and build history are read live from the ASC API on every sync. The App Store Registry tab is a cached view, never the authority.
- **SRC-2 (ios-fleet/apps.json is the source of truth for intent.)**: Canonical file: /Users/jay/apps/ios-fleet/apps.json. It says which record we mean to ship to. Drift between it and ASC is reported in the Registry tab's 'Flag' column — a non-empty flag is a bug to fix, not a note to ignore.
- **SRC-3 (Repo asset catalogs are the source of truth for icons.)**: The ASC API exposes no app-icon asset at all, so icon truth can only come from the repo's AppIcon set and 1024px marketing icon. See the Icon Audit tab.
- **SRC-4 (There is exactly one live copy of apps.json.)**: Copies inside app repos (for example trading-minimax/scripts/ios-fleet/apps.json) are mirrors and have gone stale before. The live file is the one in /Users/jay/apps/ios-fleet/. Never read a repo mirror as authority.
- **SRC-5 (Edit the generator, not the sheet.)**: The sync script owns these tabs and rewrites them wholesale. Hand-typed rows are destroyed on the next run. This section is itself generated from sheet-rules.json for exactly that reason.

### 2. Release Policy

- **REL-1 (Manual release only. Automatic App Store release stays OFF for every fleet app.)**: Owner ruling 2026-10-02: automatic release was turned off for Socratic Trade. Treat it as the fleet default. A build that passes review must never auto-publish without the owner pressing the button.
- **REL-2 (iOS ships through TestFlight until a product is deliberately released to the App Store.)**: Fleet default distribution is TestFlight. App Store availability is a per-product decision, not a side effect of a successful build.
- **REL-3 (Do not market a product as 'on the App Store' until it is actually there.)**: iOS marketing copy says Join TestFlight Beta. App Store mentions stay out of marketing copy, the trademark footer, terms.html, and privacy.html until the app really ships there.
- **REL-4 (macOS ships as a direct download, not the App Store.)**: DMG, brew, or mise. Mac App Store distribution is a separate decision per product.
- **REL-5 (Builds are produced on GitHub macOS runners, not on the owner's Mac.)**: Owner ruling 2026-10-01: 'have Mac runners on gh do all that they can for updates in general always'. Waiting on a runner is acceptable; building on Jay's Mac is not. Always keep a local-build bypass.

### 3. App Records, Retirement, And Deletion

- **ST-R1 (One product, one canonical ASC record.)**: Every app in apps.json points at exactly one appleId. Two ASC records claiming the same product is a defect, not a convenience.
- **ST-R2 (A retired record is renamed with a prefix and never uploaded to again.)**: Convention: 'IGNORE <name>' or 'RETIRED <name>'. Rename it the day it is retired so the next seat cannot mistake it for the live record. Socratic Trade's old record 6799238379 was renamed 'IGNORE old ST' on 2026-10-02.
- **ST-R3 (Never upload a build to a record that is not the canonical appleId for that app key.)**: A build sent to a retired record is invisible to the fleet and cannot be retracted. Check the Registry tab before any upload.
- **ST-R4 (Bundle IDs are immutable on an ASC record.)**: Renaming the bundle ID in code means creating a NEW ASC record. The old record can never be reused for the new bundle ID — this is what made the ST migration need a second record.
- **ST-R5 (Removing an app record is irreversible and does not free the identifiers.)**: Apple: the SKU can never be reused in the same organization, the bundle ID can never be reused if a build was uploaded, and you lose the app name (restorable only if no other developer has taken it). Removal is also blocked while the app is Ready for Review, Waiting for Review, In Review, Metadata Rejected, Rejected, being transferred, or in an app bundle.
- **ST-R6 (Before removing any record, confirm it is empty of live value.)**: Check it has no build you still need, no active TestFlight testers relying on it, no in-app purchases, and no App Clip or app bundle membership. Pause for owner confirmation — removal needs Account Holder or Admin and cannot be undone.
- **ST-R7 (Removing a live app from sale is not the same as removing its record.)**: A published app is taken off sale and keeps its record and history. Only a record that never went live is removed outright.

### 4. Bundle IDs And Naming

- **BID-1 (Bundle IDs, App Groups, and associated domains come only from domains Jay actually owns.)**: Owner ruling 2026-09-22. No invented TLDs. nslookup the domain before proposing an identifier.
- **BID-2 (No hyphens in bundle IDs or App Groups.)**: Reverse-DNS with periods only. Code filesystems and provisioning profiles punish hyphens.
- **BID-3 (Identifiers get registered before code ships them.)**: App ID, App Group, and any entitlement needing approval must exist in the Developer Portal first, then the ASC record, then code.

### 5. Icons

- **ICO-1 (Every app ships a real icon. No app is allowed to have a missing or placeholder icon.)**: Owner complaint 2026-10-02: apps with outdated or no icons 'drive me crazy and never seem to get better'. The Icon Audit tab is the standing check; a red row is unfinished work.
- **ICO-2 (One canonical 1024x1024 master per app, and everything else derives from it.)**: The master is a 1024x1024 PNG with no alpha channel and no rounded corners — Apple applies its own mask and rejects pre-rounded art. The repo's AppIcon set and the App Store icon are generated from that master, never hand-drawn separately.
- **ICO-3 (macOS needs a full icon set, not just a 1024 master.)**: macOS assets include .icns plus every PNG slot. An iOS-only AppIcon set does not satisfy a Mac build.
- **ICO-4 (A missing file referenced by Contents.json is a broken build.)**: If AppIcon.appiconset/Contents.json points at a PNG that is not on disk, the iOS build fails or ships the wrong art. The audit treats this as the highest-severity finding.
- **ICO-5 (Rebranding must regenerate icons in the same change.)**: Changing a name, palette, or mark without regenerating the icon is how icons go stale. The icon is derived output, so it is never allowed to lag the brand.
- **ICO-6 (A menu bar icon is NOT an app icon. Never put menu bar art in an app icon slot, and never 'fix' an app icon by flattening menu bar art.)**: Owner, emphatic, 2026-10-03: 'THE TRANSPARENT BLACK CODECAPS ICON IS ONLY FOR USE IN MENU BAR IF THAT IS CHOSEN AS ICON.' Menu bar art is flat black-on-transparent and tightly cropped so the system can tint and mask it. App icon art is full-colour on an opaque background. They are different assets with different jobs. Flattening menu bar art onto white, cropping it to a rounded square, or using it as the App Store 1024 all produce a wrong icon. Each app keeps its menu bar art in its own imageset, separate from AppIcon.appiconset.
- **ICO-7 (Never invent, regenerate, recolour, or substitute icon art. Only the owner or the seat the owner assigned supplies art.)**: Owner frustration, 2026-10-03: 'super fucking annoying that all these agents can't listen to simple instructions about icons.' Repeated incidents of agents re-deriving icon intent instead of reading it. If an icon is wrong, report it and name the owning seat. Do not synthesise a replacement, do not auto-flatten, and do not swap in art from a neighbouring asset. Antigravity owns the CodeCaps icon; the owner supplies the Hog Hunter icon.
- **ICO-8 (A transparent iOS 1024 is a reporting signal, not a licence to auto-fix.)**: The audit flags it because Apple rejects transparency as ITMS-90717. But the correct fix is the correct ART in the slot, supplied by the owner, never a mechanical flatten. The bundled fleet_icon_fix_alpha.py stages a flatten for inspection only and must never be run unattended or applied without the owner naming the art.
- **ICO-9 (Defined app icon place in reference sheet and editability boundary.)**: The 'Icon Audit' tab in the Google Sheet (and Section 3 of FLEET-APPS-REGISTRY.md) is the designated inventory place for fleet app icons. Generated tabs cannot be edited in the sheet — any direct cell edits are wiped on sync. Icon assets can only be edited in the repo asset catalog (AppIcon.appiconset) by the owner or assigned seat, approved with 'node fleet-icon-audit.mjs --approve', and then re-synced.

### 6. Metadata And Copy

- **CPY-1 (Two spaces between sentences in every human-readable string.)**: App names, subtitles, promotional text, descriptions, release notes, and what's-new notes all follow it. Canonical: /Users/jay/apps/FLEET-UI-COPY.md.
- **CPY-2 (Titles, headings, and button labels are Title Case.)**: Owner ruling 2026-10-01 widened this to ALL UI text including helper text, tooltips, empty states, and errors — no carve-out for status text. App Store subtitles and promotional headings follow it too.
- **CPY-3 (The product name is the brand, not a description of the category.)**: Trade naming carries the brand: Socratic Trade, Congress.Trade, DealDex, Clutch.Codes. Do not append generic category words to the name.
- **CPY-4 (Metadata is completed before a build is submitted for review.)**: Icon, screenshots, privacy nutrition label, age rating, support URL, and export-compliance answers. A rejected submission costs a review cycle.

### 7. Ship Checklist

- **CHK-1 (Confirm the target appleId in the Registry tab before every upload.)**: The single most common expensive mistake in this fleet is a build going to a retired record.
- **CHK-2 (Verify the icon audit is green for the app before shipping.)**: Missing master, missing icon slot, or stale icon blocks a clean release.
- **CHK-3 (Confirm the version and build number are correct and strictly increasing.)**: iOS rejects a duplicate build number. Marketing version and build number are separate and both matter.
- **CHK-4 (Leave automatic release OFF after submitting.)**: Per REL-1. Re-check it after any App Store Connect version edit, since the setting lives per-version.
