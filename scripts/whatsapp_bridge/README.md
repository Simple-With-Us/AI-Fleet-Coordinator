# WhatsApp Wake Bridge For Jet

AFC-477 implementation, disabled until the approved rollout.  Claude confirmed in public Work-In-Progress message 634168889 that his AFC-477 work is the merged design and spike only, with no overlapping implementation and no named Worker deployment owner.

Jay's verified WhatsApp messages wake Jet automatically, without an importance classifier.  Text beginning with `👀` after leading whitespace/invisible marks is stored but does not enqueue a wake.  An interior emoji does not suppress anything.  Non-text messages produce metadata-only inbox entries and wakes; media downloading is outside this unit.

The poller runs independently of Operator.  It sends signed batches to the Worker, which stores private text and emits content-free `whatsapp.message` events in Jet's existing conversation.  No WhatsApp content goes to Zulip.  Each event says `source: authenticated_owner` or `source: operator`; Operator events explicitly carry `owner_authorized: false`.  The owner flag describes authenticated transport provenance, never blanket approval for arbitrary actions in message text.

## Source And Tests

- `bridge.py`: standard-library sole long-poller, local flock, SQLite FULL synchronous offset, bounded schema validation, HMAC ingestion, exponential backoff and explicit processed-batch acknowledgments.  Offsets retain all signed 64 bits and advance only on an exact string match.  Startup uses offset 0 and the Worker's verified binding cutoff suppresses history.
- `binding.py`: a supervised one-time-code plus Meta creator-check helper and temporary binding mode.  `python3 -m whatsapp_bridge.binding` temporarily owns the same poller lock, requires the long-running bridge to be stopped, and leaves the durable cursor unchanged.  Running its read-receipt check live requires action-time approval.
- `operator_wake.py`: an explicit, content-free Operator doorbell with its own HMAC key and stable request UUID.  The Operator can call `python3 -m whatsapp_bridge.operator_wake <request-uuid>` from `scripts/` after its binding is approved.  Reusing the UUID is idempotent; there is no automatic retry loop.
- `../agent-sync-mcp/src/wa/`: authenticated ingestion, private read/ack tool, transactional 35-day replay tombstones, pending doorbells, content-free event delivery and body retention.

Identifiers use HMAC-SHA256 with a domain-derived ingest key, including sender and agent hashes in the binding.  The poller filters other senders before forwarding text.  Every signed batch also carries the configured sender hash; the Worker rejects any mismatch with its binding even for empty filtered batches, so misconfiguration cannot advance the cursor and lose owner messages.  JSON uses compact UTF-8 and both boundaries accept up to 8 MiB; a full 100-message emoji batch is tested.  A future-dated item is skipped by the Worker without poisoning its batch.

The exact Meta manual referenced by the design was re-read, with SHA-256 `ba677cdb476b52c9126a0e7565616131104f240b461428e8b388059a71c506e0`.  It confirms the Bearer header, updates endpoint, `user:` identifiers, signed 64-bit offsets, 30-day replay window, 204 idle response, creator check on statuses, and a competing poller producing 409.  Reference copy: [Meta Developer Manual](https://github.com/abdullah3509/whatsapp-agent/blob/main/docs/Agent%20Platform%20Guide.pdf).

## State And Failure Semantics

The bridge persists only its offset, never message bodies or credentials.  It locks the state directory locally and stops on HTTP 409 rather than fighting a poller elsewhere.  Credential/refusal errors 400, 401, 403, 404 and 413 stop it.  Network failures and 5xx retry the same offset; 429 respects numeric Retry-After, up to one hour per wait.  Three consecutive schema failures stop polling.  Redirects are refused.  The local `disabled` file stops it within the current request timeout (40 seconds), including during backoff.

The Worker atomically stores each message, its dedupe tombstone and its pending wake.  Replayed batches acknowledge the original offset even when zero messages are stored.  A paused seat still stores messages and delivers nothing.  Missing/lapsed subscribers or failed callbacks leave pending wakes for the next signed poll heartbeat.  Stable event ids let the supported MCP receiver deduplicate a retry after an ambiguous callback acknowledgment.  Bursts of the same provenance are coalesced into a doorbell.  The Worker leases delivery for 30 seconds; a crash leaves a reclaimable pending wake.  Confirmed owner delivery remains pending until an earlier read has surfaced the message and `ack_through` clears it.  One owner ring coalesces subsequent messages, with a fresh logical ring after ten minutes if still unacknowledged.  Ambiguous delivery retries keep the same event id; a confirmed re-ring gets a new generation.  A permanent callback rejection backs off ten minutes and blocks after three attempts until the subscription is refreshed.  Refresh clears the rejection block only after the existing retry delay; it cannot accelerate a ring.  Operator delivery requires its own key, independently of WhatsApp owner binding.  Explicit Operator requests/recovery claim only Operator doorbells; general delivery still prefers eligible owner messages.  Operator durably caches its queue-acceptance outcome and accepts one outstanding request and applies 30-second backpressure with an explicit 429; rejected floods add no ledger rows.  An authenticated busy Operator request attempts recovery of the previously accepted pending wake, even if the poller is down; its new id remains unaccepted.  Operator storage also arms the retention alarm.

`whatsapp_read` is Jet-only, reusing its existing read scope and enclosing text as untrusted data.  It surfaces at most 50 messages per call, returning each once unless `include_surfaced` is true.  `ack_through` is a canonical digit string and cannot acknowledge a message an earlier call has not surfaced.  The inbox uses bounded pages and durable surface/ack checkpoints.  Acknowledgment retires wakes immediately through its checkpoint, physically cleans at most 100 pending rows per call, and leaves remaining cleanup to bounded alarm pages.  It preserves permanent callback rejection blocks until subscription refresh.  Eligible owner wakes precede Operator doorbells.  Expiry jobs isolate failures so a failed deletion cannot prevent other due work.  Failed jobs move to a later due slot with exponential one-minute-to-one-hour backoff, avoiding a one-second poison-job alarm loop.  Expiry is a monotonic due-job index, not a full hourly history scan; acknowledgment deletion pages its range without per-row checkpoint lookups.  Bodies are hidden at seven days, or after acknowledgment; the hourly paginated alarm physically clears them at seven days or 24 hours after acknowledgment.  Content-free tombstones, acknowledgement checkpoints, Operator ids and expiry stubs expire at 35 days.  The separate 31-day provider timestamp cutoff rejects historical replay after ledger expiry.  Unread body expiry emits a content-free alert and leaves an expiry stub until the 35-day sweep.  Physical deletion can lag by the hourly sweep, plus pagination and platform alarm delays.  This is ordinary storage deletion, not crypto-shredding or removal from provider backups.

There is no new daily or hourly wake quota.  Meta's 30-day buffer, the callback's subscription expiry (24 hours by default in this connector), callback service limits, Worker resource/binding limits and deployment approval are real operational constraints.  A functioning bridge retries pending deliveries on its next poll; bridge downtime delays recovery.  No Worker cron or persistent service is installed by this change.

This unit implements receiving, waking and reading.  It deliberately exposes no WhatsApp reply/send tool and performs no outbound message sends, so it cannot blindly retry an ambiguous outbound message.  The design's reply outbox, send ledger, media fetching and admin binding UI remain separate work under AFC-477.
