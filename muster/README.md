# Muster

Muster is the fleet owner's native SwiftUI macOS 14+ control app.  It shows what runs on the Mac and what runs on the server as two named places, and it acts on each through a route that names the machine.

## Every Panel

Every place in the window's sidebar has one row here, and `MusterTests/ReadmeSurfaceTests.swift` fails when a place in `MusterDestination` (`Muster/Model/MusterNavigation.swift`) has no row or a row names no place.  About says which machine the panel's data describes.  The last column says what the panel can change and by which route.

A route marked **plan and Touch ID** runs the helper with `--plan` first, which changes nothing, shows that plan in a sheet, asks Touch ID, plans again and refuses if the plan changed, and only then runs `--yes`.  One such action runs at a time, app-wide.  Everything that changes the server goes over `/usr/bin/ssh` to the `fleet-ops-ctl` alias, whose forced command on the server runs `scripts/fleet-ops-control.py --from-ssh` and checks the allowlist again;  the server's helper writes its own audit row there, and Muster adds one marked `"via": "muster"` to the Mac's `~/.local/state/fleet-tools/ops-audit.jsonl`.  The allowlist is `scripts/fleet-ops-control.json`.

Muster stores no credential.  It runs `/usr/bin/python3` for the engine, `fleet-view`, `fleet-ops-control.py` and `fleet_knobs`;  `simple-chat` for Seats and Wake & Listener;  `fleet-secrets` for Controls;  pm2 through `node`, and `/bin/launchctl`, for the Services panel's reads and its direct route;  and `/usr/bin/ssh` to `fleet-ops-ctl` for the server.  Two places do read a credential, by its key name through `fleet-secrets get`, for one request, and never show or store it:  Controls' Recall Settings, for the admin token whose key name it is given, and a BotFleet host configured with an auth token.

## What PASS Means

PASS means every check the rule asks for was proven, and nothing more.  The Overview's verdict line says what its own word means once the engine has answered:  PASS is every check every rule asks for proven, FAIL is at least one check failed or could not be completed, and UNKNOWN is nothing failed but not every check was proven.  A cell in Compliance Grid shows the proof it reached, never the proof its rules required, and a dash means none was reached;  `1/2` is partly proven, with the tooltip naming the rule that was not, and `NO GUARD` means the seat has no guard, so none was checked and none was proven.  A hook rule says which guards it asks to cover.  A badge in another panel says in its tooltip what it checked:  an app row in Apps & Work, that no lane is dirty, no pull request is failing or blocked and no claim has expired;  a host in Tools And Worker Health, that the doctor's report is current, the host answered and none of its tool rows failed, are behind or could not be read.  Any other PASS covers that panel's own check on that row and nothing else.  A Mac with a cell not yet proven is never shown as OK, and the menu counts those cells beside the red and drifted ones.

## Compliance Grid

A run does not clear the grid when it starts.  The cells keep the last run's answer, and the summary and the check time stay with them, while the run checks them again;  a run that fails or times out clears them all, so nothing stale is shown as current.  A cell's tooltip says when it is the last run's answer being checked again.  A rule the last answer left out stays a finding during the next run.  An empty cell's tooltip says why it is empty:  no rule covers the pair (said only when the manifest was read and names none), the pair is being checked with no answer yet, the engine has not answered, the engine's answer has no result for the rule, the manifest was not read, or the manifest could not be read again and its last good copy names no rule for the pair.  Drawing a kept cell as being checked rather than in its last colour, and the same reasons in the detail panel, wait on a change to the grid's panels.

The manifest and the registry are read again before each run when either file's size or modification time changed, so a seat added to `fleet-seats.json` gets its row on the next run, and the watcher, which is armed again after every run, watches its paths.  A changed file that cannot be read is named, and the last copy that could be read keeps the roster.  The surfaces the engine names and does not check (the envelope's `uncovered`) and the fleet-wide rules it cannot run yet (`notImplemented`) are read too.  The MiniMax panel still treats a running engine as not answered, so it shows no hook proof and no answer time during a run.

Under each seat's tag, a chip says where the seat runs.  When the seat's entry in `fleet-seats.json` has `runsOn`, the chip names those places in plain words:  On The Mac, On The Server, On A VM or In The Cloud, joined for a seat on several, such as On The Mac And The Server for CLAUDE and ZC.  A seat that runs somewhere other than the Mac says so on its row:  when the manifest has rules for it, as it has for MA's settings file on the Mac, the row says it runs on a VM and that only what the Mac holds for it is checked here;  when it has none, as for GROK-BOT, the row says it runs in the cloud and nothing here is checked for it, followed by its cover's own sentence.  A place word Muster does not know is skipped.  A seat with no `runsOn`, or none Muster can read, is a seat whose place is not known, and its chip says Place Not Known:  its place is never guessed from its rules.  Where its rules check is a separate fact, and only that is said:  the tooltip says its rules check files on the Mac, or that no rule checks anything on the Mac for it, and a seat with no rule says so on its row, followed by its cover's own sentence.  A seat the manifest does not name is Place Not Known too.  The chip is drawn plain only for a seat that runs on the Mac, such as CLAUDE and ZC, and marked for every other, a seat whose place is not known included, so it draws the eye.

The detail panel reads the file a rule checks, and hides secret values first:  by key name (names ending `_KEY` or `_PAT` included), by the shape of a value, in lists and TOML inline tables (with or without spaces), after a flag such as `--token`, `--header` or curl's `-H`, and in a `Bearer` token, `Basic` credentials or an `Authorization:` value.  `-h`, and `Basic` or `Bearer` followed by an ordinary word, are not secrets.  A URL is a secret when it carries a password or a token before an `@`, a secret-named query value (`key`, `sig`, `signature` and `code` included), or a token-shaped path segment or query value, so `localhost:8080/mcp` shows.  A JSON file keeps its own bytes and a secret string is replaced where it stands, never in a key's place;  the file is rewritten only when that cannot be done.  A file is called redacted only when a value was hidden.  A path that is not there, one that is there and cannot be read, and a file that is not text are each told apart, and a cut inside a character still reads as text.  The note that a file was rewritten or cut off waits on the same panel change.

## Keeping Services Running

While Muster runs, it starts a service on the Mac again when it is found stopped or failed, unless Keep Services Running in Settings is turned off.  Each service has one of three policies, and its row in the Services panel says which:  Keep Running starts it again when it stops, waiting longer after every try (60 seconds, then doubling) and giving up after 3, with the count starting again once it has stayed up for ten minutes;  Start Once Per Launch starts it once, at the first look after Muster starts;  Leave Alone never starts it, which is the policy of BotFleet Server, its companion and the BotFleet MCP Server, of the Operator Eavesdropper (`com.jay.operator`, the Mac's listener, which launchd keeps alive itself), and of every LaunchAgent that is only on the allowlist.  Muster only starts a service:  it never stops or restarts one, and it never starts one the owner stopped from Muster.  Those stops are kept in `~/Library/Application Support/Muster/owner-stops.json`, service ids and times only, so quitting Muster does not forget them, and while that file cannot be read nothing is started and the Services panel says so.  An automatic start takes the same route as the owner's own Start, with the same helper, plan and audit row, but with no Touch ID, because nobody is at a sheet.  What it did is said on the service's row, in the menu and in the Services panel.

## The Menu Bar

The menu bar item names both places:  `Mac OK · Server OK`, `Mac 2 · Server OK` for two things needing attention, `Mac 2+` when something else could not be read as well, and `?` for a place not read inside its window, or one with nothing wrong and some part not read, which includes a seat cell not yet proven.  Short Menu Bar Text in Settings shortens it to `M OK · S ?`.

The menu has a The Mac section and a The Server section, and everything sits under the place it runs on.  Opening it reads memory and never contacts the server.  Ask The Server Now is the one thing that does, only on a click, and an answer never turns the bar to OK, because only a current report does that.

Under The Mac, the menu says when the Mac was last checked and counts its services.  A service that failed or is not known moves to the top.  Seat Setup lists red and drifted cells and the cells not yet proven, each opening Compliance Grid.  Services On The Mac holds every service with the Start, Restart and Stop its state allows, and Check The Mac Again reads everything again.  Under The Server, it says when the server wrote its report and when the Mac copied it, counts timers and apps, and gives the fullest disk, memory and any high load.  Timers On The Server offers Restart or Start, and Read Logs, from the allowlist;  Stop stays in the Server Status panel, because stopping the report timer would blind this section.  When the report is not current the section says why, and it offers Fetch From The Server Again… (a plan to restart the Mac's doctor agent) where a new fetch could help.

The count beside a place adds up what needs attention there.  On the Mac:  red and drifted cells, services that failed or are not known, and a stopped fetch.  On the server:  units that are not active, apps that exited or are unhealthy, each disk and the memory at 85% or more, and a load of two per cpu or more.  A part that was not read is never counted as zero.

An action that ends in … opens a sheet or an alert first.  pm2 rows, allowlisted LaunchAgents and everything on the server go through the plan and Touch ID, from the menu and the window alike, apart from the automatic start under Keeping Services Running.  BotFleet Server and any LaunchAgent the allowlist does not name stay on the direct route, with no plan, no Touch ID and no audit row.  Their Stop asks first, and BotFleet Server's Restart asks first only when a fresh read finds work in flight.

## The Window

The sidebar opens on Overview, then three sections:  The Mac (Services, Background Agents, Compliance Grid, Drift History, Wake & Listener, Seat Setup), The Server (Server Status, Resource Limits, Server Updates) and Across The Fleet (Apps & Work, Seats, Controls, Tools And Worker Health, App Processes, Virtual Machines, Action History).  Each panel's section comes from its place in `MusterDestination` and from nothing else, so a heading cannot hold a panel from another machine.  The old Operations panel is split into Background Agents, Server Updates and Action History, and a saved Operations place opens Server Updates.

Every panel has one name, the same in the sidebar, the window title and its own heading.  A strip over each panel shows one place badge, On The Mac, On The Server or Across The Fleet, and the line that says where its data came from.  The Overview's The Mac and The Server cards and Server Status's state are built from the menu's own summary of each place, in the same words, so the window and the menu cannot disagree.  Server Status shows the report's sections and their buttons only when the menu calls the report current.  When the server was reached and its report stopped, it lists the last known units with the allowlist's Restart and Logs, and when the Mac's fetch stopped or could not reach the server, it lists them with no repairs, because the menu offers a fetch instead.

## Scope

- `Muster/` holds the app:  every panel in the table under Every Panel, the menu bar item, Settings, and the models behind them, which `MusterTests/` covers without a view.
- `project.yml` is the XcodeGen source of truth.  The generated Xcode project is ignored.
- Merged changes reach the owner's Mac through Sparkle 2 from releases `.github/workflows/muster-release.yml` signs, notarizes and staples on each merge to main.  `docs/AUTO-UPDATE.md` describes the route, the feed, the gate that holds an install while an action runs, and what is still missing.
- `script/build_and_run.sh` is the developer route for trying an unmerged lane:  local project generation, signing, installation, and launch.
- The repository's `.codex/environments/environment.toml` exposes the same script through the Codex **Run** action.

Muster has no sample fleet records and no inferred health state:  a source that cannot be read shows as unknown, never as a pass or a zero.  What it runs, and the two places it reads a credential, are under Every Panel.

The Tools And Worker Health panel reads two local files and runs nothing:  the doctor's own report, which `com.jay.fleet-tools-doctor` writes every fifteen minutes and which covers the Mac and the server together, and the Worker Health report.  A report that is missing, malformed, of another version, or older than 45 minutes reads as unknown, and a host the doctor could not reach reads as unknown rather than as a failure.

## Server Status

The Server Status panel (AFC-548) reads one local file:  the server's own collector report, `~/.local/state/fleet-tools/server-status.json`, which `scripts/fleet-server-status.py` writes on the server and the Mac's doctor copies to the Mac.  It shows the host's load, memory and disks, the units the allowlist names or watches, the Coolify resources and their state, the busiest processes on the host, and the watched config files whose drift is not `unchanged`.  Its Start, Stop, Restart, Logs and Redeploy buttons run nothing on their own:  each one plans its action on the server over `fleet-ops-ctl` and asks Touch ID first, as Every Panel describes.

The collector is read only apart from that one report file, and it reads no credential:  Coolify comes from Docker's own labels and container stats, a process is identified by its executable and never by its argv or its environment, and a path that looks like a credential is never hashed and never listed.  A measurement that cannot be taken is left out of the report rather than reported as a zero, and a file that is gone reads as `missing` rather than as a zero byte file.  A report that is missing, malformed, of another version, or older than 45 minutes reads as unknown, and an empty half of the report reads as unproven rather than as a pass.

## The Action Sheet

Every action marked plan and Touch ID opens the same sheet, from the menu and the window alike.  Once the server's plan has answered, the sheet's title names what that plan named, not only what this Mac had on its button.  A Redeploy is titled with the server's own name for the Coolify resource, "Redeploy NAME on the server", unless the server has no name for it and says `coolify resource`, when the title keeps this Mac's name.  When the server's plan names a different resource from the one on the button, Muster stops the plan itself, names both, and nothing runs;  when the name changes between the review and the run, the run is refused as a changed plan and the new plan is shown for review.  A Logs read of a timer is titled with the service the timer starts, because that is the journal the server reads.  The Touch ID prompt asks with the same words as the title, so it states what the reviewed plan named, and the line at the foot of the window for a run whose sheet was closed uses them too.

The journal of a Logs read is headed by the unit the server read it from, "Logs of fleet-server-status.service" for the report timer (a timer's own journal holds only its starts and stops), with a line under it saying how many lines were read.  When the server's answer names no unit, the heading says only how many lines were read, such as "The Last 200 Journal Lines".

After a Start, Stop or Restart of a server unit is sent to the server, Muster reads that unit's state again with the read-only `server unit-status UNIT --plan` over `fleet-ops-ctl`, which changes nothing and asks no second Touch ID.  A line under the result says "Now:  reading its state on the server…" while it reads, then the state systemd gave and when the server checked it, on the owner's clock:  "Now:  active (running), checked 10:02 AM", with the date in front when it was not today.  The line ends ", newer than the server's report" when that check is later than the report the screen was drawn from, or when no report was read, and leaves it out otherwise.  When the state cannot be read, the line says "Now:  not known." and why, such as a unit the server's list does not name.  The line shows under a failed run too.  Only a server unit's own Start, Stop or Restart gets it:  a Mac job, a Redeploy, an update and a Logs read do not.

A plan to stop a LaunchAgent on the Mac always carries the general warning:  it stops right away, stays stopped until it is started here, and macOS may start it again at the next login.  Under that, the plan says what the allowlist gives for that agent, read from the Mac's agents file `~/.local/state/fleet-tools/mac-services.json`, which `com.jay.fleet-mac-services` writes and which copies each agent's `role` and `stopConsequence` from `scripts/fleet-ops-control.json` when its row gives them:  what depends on the agent, when the row gives a `role` ("This agent writes a report Muster reads." or "This agent keeps the fleet tools on the Mac up to date."), then what stopping it costs, when the row gives a `stopConsequence`.  Today `com.jay.fleet-mac-services`, `com.jay.fleet-tools-doctor`, `com.jay.fleet-worker-health` and `com.jay.simple-tools-runtime-sync` have both.  `com.jay.operator-notes-runner` has only a stop consequence, so its plan says only what stopping it costs.  When that file is missing or cannot be read, when it has no row for the agent, or when the row gives neither, only the general warning shows.

## Seats

The Seats panel (AFC-395) shows one row per seat from its own roster, grouped by the machine whose listener holds the seat in the seat partition (`docs/protocols/simple-tools-partition.toml`, or the copy the Mac's listener names):  Held By The Mac, Held By The Server, Held By No Eavesdropper.  Each row shows the live sessions the Mac's listener holds for the seat (with each session's letter, title, platform and verified machine), the listener's state for it with any running wake and its last event, the provider quota the listener reads for it (the same reading its wake gate uses), and its last Zulip post.  The panel leads with a sentence that says how many Mac seats are connected and working, and every column names its source and its time on screen.

A session the listener reports with no letter reads No letter reported:  the listener leaves the letter out both when the session never registered one and when its registry lookup failed, and it does not say which, so the panel claims neither.  A session that has not ended says when no rewake watcher holds its lease (a new message will not wake it again), or that the listener did not say.  Under the headline, the panel says whether resume-wake is verified on this Mac for terminal and Desktop sessions (`rewake_verified_cli` and `rewake_verified_desktop`), from the same listener state as the rows.

The panel's roster is its own and is wider than the Compliance Grid's, which it never changes:  the grid's seats first, then the registry's live seats, its extra seats (`seatApps.extraSeats`, such as AMP and JET) and the BotFleet and Grok Bot seats its `BF-*` and `GB-*` patterns name role by role, each when the seat partition gives it to the Mac or the server, and every other seat the partition gives to the Mac or the server.  Each seat is listed once.  A retired name, an alias, the `GROK-BOT` group tag and any name the partition marks `none` are never rows, whichever source names them, unless the Compliance Grid itself lists that seat.  A second login of a seat that the partition does not list, such as `JET-CHAT` for Jet, is not a row of its own.  The Operator (`OPERATOR`) is a service with no queue, not a seat, so it is not a row either:  Wake & Listener shows whether it can post, and Services shows the Operator Eavesdropper.

The Seats panel shows only the Mac's listener today.  A seat the server holds says Not read here in its listener columns, in plain text, because that is where the seat lives and not a fault, and its tooltip says the server holds it.  Sessions shown are on the Mac only.  The model and the route that read the server's listener status are in place:  the read-only verb `server eavesdropper-status server --plan --json` over the restricted `fleet-ops-ctl` route, for which the server's helper reads the listener's status inside its container and cuts it down to names, counts, tokens and times (the `reduced_status` v1 document);  the verb changes nothing, needs no Touch ID and accepts `--plan` only.  Muster reads every field of that document as optional, so a missing or null field reads as Not reported and never as zero or connected;  a document of another version, or one that does not say it is the server's, is not read;  and a reading whose answer or listener status is more than five minutes old is not current, offers its facts only as the last known ones and never says a seat is not listed.  The helper with that verb is deployed on the server (PR 1479).  The Seats panel shows the server's seats from it once the panel is wired to it;  until then the server's seats are not read, and a helper without the verb answers that it does not know it.

Sources:  the listener's own published state at `~/.simple-tools/listener/status.json` (believed only when it says it is the Mac's instance and was written in the last 60 seconds), its configuration file, the seat partition, and the fleet chat CLI's read-only Operator service (`simple-chat muster-service`).  The panel runs the service's `users` and `last-post` subcommands and nothing else;  `ChatCLI` refuses any other before a process exists,  so the panel cannot write to Zulip.  It no longer asks for Zulip presence, because Zulip refuses presence for bot users.  The service can only send GET requests for `users/me`, `users` and `messages`.

Muster reads Zulip only as the Operator service bot (owner ruling, AFC-654), never as an agent seat and never as Jay.  There is no seat to choose:  the Settings choice, the `CLAUDE` default and `MUSTER_ZULIP_SEAT` are gone, and a seat an older build saved is removed at launch.  The service reads the Operator's own credential from Fleet-OPS `/zulip_operator`, checks the stored realm, and verifies `users/me` against the host's pins before it reads anything:  `operator_user_id`, `operator_email` and `owner_user_id` under `[daemon]` in `~/.simple-tools/listener.toml` (the environment's `OPERATOR_ZULIP_USER_ID` and `OPERATOR_ZULIP_EMAIL` win when set).  The app never sees a key.  When the Operator read is unavailable (a missing pin, an unreadable credential, a wrong identity, or an older `simple-chat` without the service), the panel says so in plain words with the reason, shows every last post as unknown, and reads nothing as anyone else.  `last-post` reads only the sender's newest post in a public channel, so direct messages and private channels are never read.  See `docs/muster-operator-zulip.md`.

A refresh makes at most one `users` call and one `last-post` call per seat, so the ceiling is `1 + seats`, and nothing for an empty roster;  the counts are under Details.  The reading is held for the whole app, so returning to the panel shows the last reading and reads again only when it is more than a minute old, one read runs at a time, and the five-minute timer reads only while Muster is in front.  A source that fails leaves its column Unknown with the reason under the row:  a missing binary, a refused call, an unreadable file and a listener state file more than 60 seconds old all read as unknown, never as "no sessions".  An empty roster says Muster has no seat list instead of showing zeros.

## Wake & Listener

Each seat has one wake path, by the owner's ruling of Nov 10, 2026:  a signed wake the listener sends to the seat's routine, which wakes the right chat, picking among the seat's chats by letter, topic words or recency, or waking the seat's only thread.  Until the listener change lands, today's listener still decides by the old `wake` line (`simple_tools/config.py`):  no line is inbox, a routine is read only with `wake = "http"`, and every other mismatch drops the seat to inbox, which only captures.  So a seat Wakes when its `[seat.X]` section holds a routine table, as `routine = { … }` or under a `[seat.X.routine]` header, with `wake = "http"` or with no `wake` line, which is how the one-wake-path listener reads every seat once the line is gone.  It Captures Only when it holds no routine and no `wake` line or `wake = "inbox"`:  its mentions are kept in its inbox, and nothing is woken.  Every other mix is an Old Wake Setting, and the panel says what today's listener does with it:  with no routine, it still wakes `claude`, `muse` and `openrouter`, and refuses `http` or a word it does not know, so that seat only captures;  with a routine and a wake other than `http`, it ignores the routine, so that seat only captures until the listener change lands.  Muster offers no control for the old keys, never writes a `wake` line, and mentions a `wake` line beside a working routine, read only, as left over from the old wake types.  A routine line that is not a table, a routine written both ways at once, or a line in the seat's section Muster can't read (such as a dotted `routine.url_env` key) leaves the seat Not Known, and it needs a look.  A seat another listener holds, or one with no section in the Mac's file, is Not Known too, with nothing in the file to look at.

For a seat that Wakes, the panel can change the routine's `url_env` and `key_env`, which are the names of the environment variables that hold the routine's address and the key that signs each wake, never their values, and its `timeout_seconds`, from 1 to 60.  A change to either variable asks for Touch ID, because it changes where the seat's wakes go or how they are signed.  The method, the signing and the header are fixed by the router contract (POST, a bearer key, the Authorization header), so they are shown and never offered;  a seat whose file says otherwise is marked as differing from the router contract.  Muster checks a routine edit with the listener's own rules before `daemon check-config` runs:  it refuses a name that is not a variable name, the CLI's own single-seat variables, the same variable for both, and a timeout out of range.  It writes a routine setting only into a routine table the seat already has, in the form the file already uses, and never takes the table out, so it never turns a seat that Wakes into one that Captures Only.  Giving a seat that Captures Only a routine is not offered:  it waits on the listener change that drops the old `wake` line.  The `budget` and `live` caps apply to a seat that Wakes, or to one whose old wake today's listener still runs;  a cap the file holds for a seat that Captures Only is still shown.  Caps kept under their own `[seat.X.budget]` or `[seat.X.live]` header are read and written there, in place.  The five wake caps in `budget` (`wakes_per_hour`, `wakes_per_day`, `per_topic_per_hour`, `owner_per_day` and `owner_per_topic_per_hour`) have no default since #1735:  a cap the seat leaves unset reads No Limit, in the file's column and in the listener's, because the listener's status then carries none, and clearing the field is the plain way to choose it.  A cap of 0 reads Paused, and no wake of that kind is allowed while it is 0;  a positive number is a cap.  The `live` caps keep the listener's defaults, so a `live` cap of 0 is refused where the listener compares with at or over (`per_hour`, `per_day` and `owner_per_day`), because it would stop every live turn;  the live loop turns and minutes per topic take 0 as off.

Test Wake is shown for every Mac seat and is off for now.  It waits on the listener's new dry run, which shows the chat a wake would reach and why, without waking it, and for a seat that Captures Only, whether the listener captured it.  Nothing in the panel runs `daemon test-wake`, runs an agent, posts a message or spends a wake.  The listener's status says whether each seat's routine can be reached, and the panel shows that beside the seat;  a seat that Wakes that the listener reports with no routine says so.

The panel believes the listener's status as current only when the listener is running, the status says it is the Mac's instance, and it was published in the last 60 seconds, the same rule Seats uses.  A status another instance wrote is named in the problem box and in the header's not-current line, and is never shown as the Mac's:  its list of seats turned off does not mark a Mac seat SEAT OFF.  Under a status that is not current, each seat's held-back wakes, red warnings, chat nudges, quota and routine readiness are shown as the listener's last word, as of the time it published, marked not current, and never with the word now.  Times that may not be today, such as when a pause was set and when a quota resets, carry the weekday and date on Jay's clock.

The pause a seat is under comes from a current status, and otherwise from the kill switch file itself, `~/.simple-tools/listener/pause.json`.  A pause file that is not there is no pause, as the listener reads it, whatever an old status still lists.  Only when the file was not read is the last status used, marked not current.  A pause file that cannot be read leaves the pause not known, never unpaused, and the seat's Pause Wakes and Resume buttons are shown off, with why.  The pause named is the one that has the effect:  a full pause in either scope, the seat's own or every seat's, before a wakes-only one, by the same rule Seats uses.

Held-back wakes the listener lost past both its caps and still owes are shown as a problem and put the seat under Problems Only, with the ones kept in the overflow and the lifetime expired and lost counts beside the queue.  The panel also says whether resume-wake is verified on this Mac, only from a current status:  a stopped listener resumes nothing.

The Operator section says the file was not read, and that its Operator section is not known, when the configuration file is there and cannot be read, instead of saying the file has none.  A configuration file that is not there holds no Operator section, and the section says so.  A lower-case `[seat.operator]` section is the Operator's, as it is to the listener, and its rules are checked:  bot Operator, creds infisical, and no routine table, because the Operator Captures Only.  Below it, the Decider line shows the one decider every platform shares, which runs only when a seat's routine cannot pick the chat by letter, topic words or recency:  the runtime and the model slug of `[muse_bridge] consult_backup`, read only, never a key, or No decider is set.  Changing it is a deliberate edit of `listener.toml`, because its slug has to match `expected_models`.  The host load gate shows nothing in the file's column when the file holds no `host_wake_load_per_core`, and says the listener's default, 0, which is off, is in effect.

## Drift Alerts

The app watches the paths the manifest names and says when a cell turns red.  It is idle between refreshes:  FSEvents is the only thing that wakes it,  and there is no poll of any file's contents.

The watch list is **derived from the manifest**,  never written down:  every rule's `check.target` becomes a path,  `~` is expanded,  and a rule that checks a credential is skipped because the app never reads a credential.  A new seat is watched because the manifest names its paths.  Each path is watched by its own path,  which FSEvents filters to that path alone;  a path that is not there yet is watched too,  and FSEvents reports it when it appears.  The nearest directory above it is watched as well,  unless that directory is the home directory:  FSEvents watches a directory recursively,  and the home directory is the largest tree on the Mac.

A change is gathered for a second and a half,  so a write that lands in two pieces is one run,  and the engine runs again.  Runs that a watched change asks for are at least a minute apart: a change inside that minute waits for one run at the end of it, so a file that is written all the time, such as `~/.claude.json` while Claude Code runs, costs one run a minute and not one run a write.  The safety net and a refresh the owner asks for are not held back.  The watch list is built again after every run, and the watches are armed again only when it changed, when a watch could not be armed the last time, or when a stream the watcher had started is no longer running.  A slow safety net looks at the clock every minute and runs the engine when no trusted run has landed for ten minutes, on the wall clock, so a sleep counts;  after a run that failed it waits ten minutes before trying again, and it never starts a run while one is in flight.  When the Mac wakes, the engine runs ten seconds later, once the network is back, unless a trusted run that started after those ten seconds already covers it;  a run that started before the sleep or inside the ten seconds never covers it, even when it lands after the wake, and a run still in flight that started that early gets one more run behind it.  A watched change inside the ten seconds starts no run of its own:  the wake's run reads it.  A gap of more than two minutes between the safety net's looks means the Mac slept, so when the safety net is due at that look its run also waits the ten seconds, even before the wake notice arrives.  The watcher counts only the streams that started:  a path whose stream would not start is counted as not watched.  A cell that was not red and becomes red posts one notification that names the seat and the check;  a cell that stays red says nothing again,  and a cell that recovers and turns red again says so again.  A fleet-wide compliance rule that starts failing (DRIFT, MISSING, or an UNKNOWN) posts a Compliance Alert the same way, once per rule and place, and goes into the same history.  The notification fails soft:  an app without permission,  or a process without a bundle,  records the turn and posts nothing.  The menu bar item counts red and drifted cells among the things needing attention on the Mac, in plain words, with no colour of its own.

The first run that could be trusted is a reading and not a change:  there is no earlier answer to compare it with.  A run that could not be trusted says nothing,  and the count is unknown rather than zero.

## Build And Run

From the repository root:

```sh
./muster/script/build_and_run.sh --verify
```

This is the developer route, for a lane on a Mac.  The owner's copy is delivered by the release workflow, never by this script.

The build number is the 12-digit `YYYYMMDDHHMM` time of the commit being built, in UTC, read from git.  The script also stamps the commit, its time and a channel into the Info.plist:  `main` for a clean tree whose commit is on `origin/main` as last fetched, `lane` otherwise (Settings and the menu then say Not From Main), and `development` for `--development`.  `MUSTER_BUILD_NUMBER` overrides the number, and a malformed override refuses before anything runs.  A build numbered below the installed copy is refused unless `--allow-older` is given, because Sparkle would then offer the newer release again.  Marketing version and signing settings remain those in the project.

The default Release configuration builds `services.jays.Muster` with Developer ID signing and hardened runtime enabled.  App Sandbox is disabled to leave room for the separately owned CLI integration; the app currently has no capabilities or custom entitlements.

The script installs the sole normal app copy at `~/Applications/Muster.app`, launches that bundle, and verifies its exact executable path with `--verify`.  Its `dist/` staging directory is removed when the script exits, including on failure.  Installation prepares and verifies a copy on the destination filesystem before replacing the installed bundle, and restores the previous bundle if replacement or verification fails.  Incremental build data stays under ignored `muster/.build/`.

If Muster is already running, the script stops before building.  Quit it manually, or explicitly authorize this invocation to terminate only the installed copy:

```sh
./muster/script/build_and_run.sh --verify --relaunch
```

The script never force-kills a process.  A second concurrent invocation fails against a local lock; after an interrupted process, inspect whether a build is still active before removing `muster/.build/run.lock`.

Optional modes are `--logs`, `--telemetry`, and `--debug`.  Log modes stream unified logs after launch;  `--telemetry` shows Muster's own subsystem, whose one category today is `drift`, from the drift monitor.  The build lock and staging are released before a log stream or debugger blocks.  Debug mode attaches LLDB to the installed process and is subject to macOS Developer Tools permissions and hardened-runtime debugger restrictions.

Full local builds follow the repository build coordination protocol.  The script is an on-demand developer helper, not an always-on service.

## Development Identity

```sh
./muster/script/build_and_run.sh --development --verify
```

Debug uses `services.jays.Muster.dev`, a distinct development bundle ID.  Both configurations deliberately install to the same `~/Applications/Muster.app` path so they cannot leave multiple normal app copies.  Run the default Release command after quitting a development build to replace it with the stable identity.  A Debug build carries no update feed, so it never updates itself;  a Release lane build does, and the next release from main with a larger build number replaces it.

These bundle IDs are working choices pending product identity onboarding.  They are not a finalized fleet registry, Apple portal, or distribution registration.

## Apply Preview

`FleetConfigCLI.swift` is the one wrapper around the engine:  `/usr/bin/python3 -m fleet_config <verb>` run from the repository's `scripts/` directory, arguments as an argv array, output decoded tolerantly.  Any view can call a verb through `FleetConfigRunning`.  `ApplyCoordinator.shared.beginPlan(seat:ruleID:kind:)` is the entry point for a red cell:  it runs `apply SEAT KIND --plan`, shows the planned writes in `ApplyPlanView`, asks once, then runs `apply SEAT KIND --yes` in the background and re-proves with `status --json --seat SEAT --kind KIND --no-doctor`.  The apply is owned by the app-lifetime coordinator, not the view, so closing the sheet or window does not cancel it, and a notification reports the result.  A refusal (Touch ID declined or unavailable, a manifest rule that is not auto-fixable, an engine refusal) leaves the cell red and is never retried.

The Touch ID gate for persistence-class writes lives inside the engine, behind a fixed-path signed helper.  Muster neither reimplements nor bypasses it, passes no helper path, and strips `FLEET_CONFIG_*` and `PYTHON*` variables from the child environment.  Muster has no URL scheme, AppleScript, App Intents or Shortcuts entry point, and `script/test_no_external_entry_points.py` keeps it that way.

The repository root is a setting:  the `fleetConfigRepoRoot` user default (`defaults write services.jays.Muster fleetConfigRepoRoot /path/to/repo`), then the `MUSTER_REPO_ROOT` environment variable, then `~/Code/AI-Fleet-Coordinator`.  Settings shows it under Folders, as Fleet Checkout, with the folder in use and where it came from, and the scripts folder the same way, as Fleet Scripts (`musterScriptsDir`, after `MUSTER_SCRIPTS_DIR`).  Choose Folder… sets either one, and Use Default clears the choice.

Apply unit tests are an XcodeGen target that compiles the non-view sources directly, so the tests need no signing of their own.  The scheme still builds the Developer ID app target, so the command passes the same signing overrides as the CI job named Muster macOS build, and this is the command that job runs.  The same target decodes the server, Worker Health and LaunchAgent fixtures in `MusterTests/Fixtures/` (current, old shape, malformed and stale), drives the operations flow with an injected runner, so no test starts a process or asks Touch ID, and checks this README's Every Panel table against the app's places:

```sh
cd muster && xcodegen generate --spec project.yml
xcodebuild -project Muster.xcodeproj -scheme Muster -configuration Debug \
  -destination 'platform=macOS' -derivedDataPath .build/CITest \
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY= test
```

## Hog Hunter On This Mac

The Background Agents panel shows what the Hog Hunter Mac app says about this Mac: load, CPU, memory, swap, each mounted volume, the busiest processes by name, the last cleanup, the housekeeper lock, the cleaning regimen, the age of the server snapshot Hog Hunter holds, and its version.  The source is one local file the running app writes about once a minute, `~/.local/state/fleet-tools/hoghunter-mac.json` (tool `hoghunter-mac-status`, schemaVersion 1; decoder `Muster/Model/HogHunterMacReport.swift`).  Muster only reads it and has no control of Hog Hunter: no command, no connection and no credential.  The file's authentication is the file system: Muster reads it only when it is a regular file (not a link), owned by the current user and not writable by group or others, and no larger than 256 KB.  A missing file or a report older than 5 minutes reads as unknown, and the panel says Hog Hunter is not running or has not reported.  A file that fails the ownership or link check, a wrong version or tool, or a malformed file reads as unknown too, but states its own reason instead.  Fields the app could not measure are absent and show as Not reported, never as zero.

## Delivery And Build Identity

Muster updates itself through Sparkle 2.  `.github/workflows/muster-release.yml` builds, signs, notarizes and staples each merge to main that changes `muster/`, and installed copies read Muster's own feed, the fixed `muster-feed` release, once an hour.  An automatic install waits until no apply, operations run or service action is in flight and Muster is no longer the app in front.  An Install And Relaunch the owner chooses waits only for work in flight.  `docs/AUTO-UPDATE.md` has the whole route.

Settings ▸ This Build and the foot of the menu show the version, the build number and the short commit, with Development Build or Not From Main when that applies, and the commit of the checkout Muster runs its Python from, saying plainly when the two differ.

The route is proven end to end:  Muster's own Sparkle key and its read tokens exist, every merge to main that changes `muster/` publishes a signed release, and on Nov 7, 2026 the installed copy adopted published build 202611071913 on its own.  The feed release, `muster-feed`, is pinned as the repository's latest release, so a Muster build never is.  The receipts and the rotation dates are in `docs/AUTO-UPDATE.md`.
